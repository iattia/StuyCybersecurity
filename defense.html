Blue team

Defense and incident response

Defensive security is the work of reducing risk, noticing when something goes wrong, understanding what happened, limiting damage, and improving the system afterward.

Prevention is only one part

No organization prevents every mistake or attack. Good defense uses several layers: secure design, strong identity controls, careful configuration, updates, backups, monitoring, trained people, and a practiced response plan.

A control should have a clear purpose. A firewall can limit network paths. MFA can reduce account takeover. Application allowlisting can restrict execution. Logging can preserve evidence. Backups can support recovery. One product rarely solves several unrelated problems equally well.

Know what you are protecting

Asset inventory comes before monitoring. List important devices, accounts, services, applications, data, owners, dependencies, and normal business use. If a system appears in a log but nobody knows what it is, response will be slow and uncertain.

Classify what would happen if confidentiality, integrity, or availability were lost. A public club website and a database of student records do not have the same consequences or access requirements.

Useful logs include reliable timestamps, event types, actor and target identifiers, outcome, source system, and a request or correlation ID. Avoid storing passwords, session tokens, or unnecessary personal data.

From a question to a detection

A detection should describe behavior that matters. “Malware happened” is not testable. “A document process started a command shell that connected to a new external destination” is closer to observable behavior.

  1. State the threat behavior and why it matters.
  2. Identify the required data sources and fields.
  3. Write a query against known test data.
  4. Measure expected benign matches and add justified context.
  5. Create alert output that gives an analyst enough evidence to begin.
  6. Test with a safe simulation and maintain the rule as systems change.
Detection goes beyond matching known strings

An IP address or file hash can be useful, but it may stop being useful quickly. Detections based on behavior, identity context, sequence, rarity, and asset importance usually remain relevant longer.

Alert triage

Triage asks whether an alert represents expected activity, a policy issue, a failed attempt, or an incident requiring action. Begin with the alert logic and raw evidence. Confirm the user, device, time, process tree, network activity, and affected resource. Compare with normal behavior and related alerts.

Do not label something a false positive merely because it was benign. If the rule accurately detected the behavior but the behavior is allowed, the rule may need better context or the environment may need a documented exception.

Incident response

PhaseMain workQuestions
PreparationRoles, access, tools, contacts, logging, backups, exercisesCan the team act safely and quickly?
IdentificationValidate evidence, scope affected assets and accountsWhat happened, when, and with what confidence?
ContainmentLimit ongoing harm while preserving essential operationsWhat action reduces risk without destroying evidence?
EradicationRemove persistence, close the initial weakness, reset trustWhat caused the incident and what remains compromised?
RecoveryRestore service, monitor closely, validate normal operationWhen is it safe to return and how will recurrence be noticed?
Lessons learnedUpdate systems, detections, process, training, and documentationWhich change would most reduce future risk?

Real phases overlap. A team may contain one account while still investigating other systems. Keep a timeline of decisions, evidence, and actions. Know who has authority to isolate a device, disable an account, communicate externally, or involve legal and law enforcement.

Threat intelligence

Threat intelligence supports a decision. It may describe an adversary, campaign, vulnerability, technique, target, or indicator. Useful intelligence states its source, date, confidence, relevance, and expected action.

Do not paste every public indicator into blocking systems. Indicators can be stale, shared by legitimate services, or intentionally misleading. Validate them against internal evidence and the organization's risk.

A safe club lab

  1. Create a local virtual machine and enable process, login, and network logging.
  2. Perform normal actions such as opening an editor, using a browser, and running a script.
  3. Run a harmless simulation such as repeated failed logins against a local test account.
  4. Write a query that distinguishes the simulation from ordinary events.
  5. Create an alert containing time, account, host, count, and source.
  6. Write a short incident note and propose one preventive control.
