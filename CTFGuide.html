Capture the Flag: A Practical Guide

A detailed introduction to solving cybersecurity challenges, learning the underlying ideas, and working well with a team.

Prepared by Ibrahim Attia · 2026 edition · For legal, educational practice only

How to use this guide

This is meant to be read in two different ways. If you are new, begin with Part I and work forward. The early chapters explain the ideas that later chapters assume: files, terminals, networks, bytes, and small Python programs. If you are in the middle of a competition, use the table of contents or search box to jump to the category you need.

You do not have to memorize the commands. You should understand what question each command answers. When you use a tool, write down what you expected, what happened, and what the result tells you. That habit is more important than having a large toolkit.

Stay within the rules.

Only test systems and files that a CTF organizer explicitly provides, systems you own, or systems you have clear permission to assess. Do not aim scanners, payloads, password tools, or exploit code at school systems, public websites, other players, or any third party. A CTF is a controlled learning environment. Keep the techniques inside that environment.

If you are starting out

Getting stuck is normal and often useful. Notice what you know, identify what you still need to learn, and choose a small next step that will give you new evidence.

Part I

Foundations

These chapters build the basic mental model you will use in every category. You can solve beginner challenges without knowing all of this, but learning it now will save you from guessing later.

Chapter 1

What a CTF is and how to approach one

A Capture the Flag competition is a set of controlled cybersecurity problems. Each problem asks you to discover a special string called a flag. The flag proves that you reached the intended goal.

Common competition formats

Most student competitions use the Jeopardy format. Challenges are grouped by category and assigned point values. Your team can usually work on several problems at once. Easier problems may be worth fewer points, while difficult problems are worth more. Some events use dynamic scoring, so a challenge becomes worth fewer points as more teams solve it.

In an attack-defense competition, every team runs the same vulnerable services. Teams must keep their services available, fix weaknesses, and exploit opposing teams. This format requires more operations and defensive skill than a typical beginner event.

Other events use king-of-the-hill, hardware, scavenger-hunt, or mixed formats. Read the rules before assuming that habits from one event apply to another.

The usual categories

CategoryWhat you studyTypical evidence
WebHTTP, browsers, sessions, databases, application logicRequests, responses, cookies, source code, API behavior
CryptographyEncodings, ciphers, randomness, number theory, implementation mistakesCiphertext, keys, parameters, mathematical relationships
ForensicsFiles, metadata, packet captures, disks, memory, timelinesArtifacts that reconstruct what happened
Reverse engineeringProgram behavior, assembly, decompilation, debuggingControl flow, constants, comparisons, runtime state
Binary exploitationMemory corruption and program defensesCrashes, offsets, leaks, controlled instruction flow
OSINTCareful research using public informationSources, dates, identities, locations, archived records
MiscellaneousScripting, logic, unusual data formats, puzzlesWhatever the problem makes available

What the point value does and does not tell you

A point value is an estimate, not a law. A difficult challenge may become easy if it matches something you have studied. An easy challenge may take a long time if it uses an unfamiliar tool. During a competition, use point values to help allocate team time, but do not let them decide what you are capable of learning.

Read the rules before touching a tool

Check which hosts, ports, files, and accounts are in scope. Look for rate limits, restrictions on automated tools, rules about collaboration, and rules about publishing solutions. Some practice platforms ask learners not to post complete write-ups because the same challenges are used in courses. Respect that request.

Practice

Open the rules page for a current or archived CTF. Write down the flag format, team-size limit, scoring method, allowed targets, prohibited behavior, and write-up policy. If any one of those is unclear, you are not ready to begin the event.

Remember

  • A CTF is a legal, controlled environment, not permission to test unrelated systems.
  • Categories describe the main skill being tested, but many challenges combine categories.
  • The rules and scope are part of the challenge.

Chapter 2

Setting up a safe working environment

A good environment makes experiments repeatable and keeps challenge files separate from your personal data. Start simple. Add tools when a challenge gives you a reason.

Choosing an operating system

Linux is the most convenient environment for many CTF tools. You can use a Linux computer, a virtual machine, or Windows Subsystem for Linux. macOS works well for shell, Python, web, and many forensics tasks, although some binary tools and challenge executables expect Linux.

  • Linux computer: simplest if you already use Linux.
  • Linux virtual machine: strong isolation and easy snapshots. Give it only the folders and network access it needs.
  • WSL: convenient on Windows for command-line work. A full VM may still be better for unknown binaries, kernel challenges, or tools that expect a normal Linux system.
  • macOS: fine for most beginner work. Use a Linux VM when binary compatibility matters.

A sensible folder structure

terminal
ctf/
  event-name/
    README.md
    web-100-example/
      original/     # untouched downloads
      work/         # copies you edit or extract
      scripts/      # code you write
      notes/        # requests, screenshots, reasoning
      solution.md   # final explanation

Keep original files unchanged. If you modify an image, patch a binary, or extract an archive, do it under work/. This makes it easier to restart and lets teammates verify your steps.

Record hashes

A cryptographic hash is a compact fingerprint of a file. Hashing the original tells you whether a file changed and lets teammates confirm that they received the same artifact.

terminal
# Linux
sha256sum original/*

# macOS
shasum -a 256 original/*

# Copy an artifact before working on it
cp original/challenge.bin work/challenge.bin

Unknown files and programs

Do not run an unknown executable on the computer that stores your passwords, schoolwork, browser sessions, SSH keys, or personal files. Use the environment provided by the organizer or a disposable virtual machine. Turn off shared clipboard and shared folders if the risk is unclear. Take a snapshot before running the file.

Tools worth having at the beginning

You do not need every security distribution package. A small base is enough:

  • A terminal, Git, Python 3, and a code editor.
  • file, strings, xxd, curl, wget, nc, ssh, tar, unzip, and 7z.
  • Browser developer tools and an intercepting proxy for web practice.
  • Wireshark or TShark for packet captures.
  • GDB and Ghidra for Linux binaries.

Install category-specific tools when the relevant chapter introduces them. This helps you understand why they are useful instead of treating the toolkit like a magic box.

If setup is slowing you down

Ask a teammate for a known-good environment or use the browser-based environment supplied by a training platform. Learning how a tool works matters more than spending the entire meeting repairing one laptop.

Chapter 3

Linux and the command line

The shell is a way to combine small programs. CTF work becomes much faster once you can move data from one program to another without doing everything by hand.

Paths and navigation

A path identifies a location in the filesystem. An absolute path starts at /. A relative path starts at your current directory. The names . and .. mean the current and parent directory.

navigation
pwd                 # print the current directory
ls                  # list names
ls -lah             # include hidden files, sizes, and details
cd work             # enter a relative path
cd ..                # move to the parent
find . -maxdepth 3 -type f -print

Reading files without damaging them

  • cat is fine for a short text file.
  • less is safer for long output. Search with /pattern and quit with q.
  • head and tail show the beginning or end.
  • xxd shows raw bytes in hexadecimal.
  • file guesses a format from content rather than the filename.
  • strings extracts printable sequences from binary data.

Standard input, output, and errors

Most command-line programs read from standard input and write normal results to standard output. Errors usually go to a separate stream called standard error. A pipe, written |, sends one program's output into another program's input.

pipes and redirection
strings -a mystery.bin | less
strings -a mystery.bin | grep -iE 'flag|pass|secret'
command > output.txt          # replace a file with standard output
command >> output.txt         # append standard output
command 2> errors.txt          # save standard error
command > all.txt 2>&1        # save both streams
tee copy.txt                   # show output and save it

Searching effectively

grep searches text. find searches directory entries. Do not confuse them. Start with literal text, then add regular expressions if needed.

search examples
grep -n 'admin' page.html
grep -RIna --binary-files=without-match 'picoCTF{' .
find . -type f -name '*.txt' -print
find . -type f -size +1M -print
find . -type f -newermt '2026-01-01' -print

Permissions

Linux tracks read, write, and execute permission for the owner, group, and everyone else. ls -l displays them. A downloaded challenge binary may need execute permission:

permissions
ls -l challenge
chmod u+x challenge
./challenge

The ./ matters because the current directory is usually not searched automatically for commands.

Processes, ports, and remote connections

process and connection basics
ps aux
ss -lntup
nc CHALLENGE_HOST 31337
ssh USER@CHALLENGE_HOST -p 2222
curl -i https://challenge.example/

Netcat creates a plain TCP or UDP connection. SSH creates an authenticated, encrypted terminal session. Curl speaks application protocols such as HTTP and prints the response. Use the tool that matches the service.

Quoting and expansion

Shell quoting causes many avoidable errors. Single quotes preserve text literally. Double quotes still allow variables such as $name to expand. An unquoted space separates arguments. If you are not sure what the shell will do, place the data in a file or print the command before running it.

Practice

Create five small files, hide a string in one, compress the directory, and give the archive a misleading extension. Ask a partner to identify the format, list the archive without extracting it, extract it safely, and find the string using a pipeline.

Chapter 4

Networking concepts you will actually use

Networking is easier when you separate layers. An IP address identifies a network interface, a port identifies a service endpoint, and an application protocol gives meaning to the bytes that cross the connection.

A useful layered model

LayerMain questionExamples
LinkHow does a frame reach the next device on the local network?Ethernet, Wi-Fi, MAC addresses, ARP
InternetHow does a packet reach another network?IPv4, IPv6, ICMP, routing
TransportHow do applications exchange streams or datagrams?TCP, UDP, ports
ApplicationWhat do the bytes mean?HTTP, DNS, SSH, TLS, SMTP

IP addresses and ports

An IP address alone does not identify a program. A TCP or UDP port number distinguishes services on the host. The pair of source IP and port plus destination IP and port identifies one direction of a conversation. Packet tools often call these endpoint pairs a flow.

Ports suggest a protocol, but they do not guarantee it. HTTP commonly uses 80 and HTTPS commonly uses 443, yet a CTF service can run anywhere. Inspect the traffic or interact carefully instead of trusting the number.

TCP and UDP

TCP provides an ordered byte stream. It uses sequence numbers, acknowledgments, retransmission, and a connection setup. Applications do not receive TCP “messages”; they receive bytes, which is why an application protocol needs its own way to mark lengths or boundaries.

UDP sends individual datagrams without TCP's delivery and ordering guarantees. DNS often uses UDP for ordinary queries and TCP in cases such as large responses or zone transfers. Real protocols may use either transport depending on the situation.

DNS

The Domain Name System maps names to records. An A record contains an IPv4 address, AAAA contains IPv6, CNAME aliases one name to another, MX identifies mail servers, and TXT stores arbitrary text used by many systems. CTFs sometimes hide clues in unusual records or query names.

DNS questions
dig example.com
dig example.com A
dig example.com TXT
dig +short example.com
nslookup example.com

TLS does not replace application security

TLS protects traffic in transit between endpoints. It can provide confidentiality, integrity, and server authentication. It does not prove that the application has correct authorization, safe queries, secure business logic, or honest users. In a web challenge, seeing HTTPS does not mean you should stop looking for application problems.

Network enumeration in scope

If the organizer gives you a host and allows scanning, begin with the smallest scan that answers your question. A service-version scan against listed ports is easier to interpret and less noisy than immediately scanning every port with every script.

scoped example
# Replace the placeholder only with an explicitly authorized challenge host
nmap -sV -p 22,80,443 CHALLENGE_HOST
When a connection fails

Check the hostname, port, protocol, VPN requirement, and event status before assuming the service is exploitable. Try to distinguish “my network cannot reach it,” “nothing is listening,” and “the application rejected my request.” Those are different problems.

Chapter 5

Python, bytes, and small scripts

Python is useful because CTF problems often involve transforming data. A ten-line script that shows every intermediate value is usually better than a clever one-liner you cannot debug.

Text is not the same as bytes

A Python str represents text. A bytes object represents values from 0 through 255. Files, network sockets, hashes, ciphers, and machine instructions operate on bytes. Encoding converts text to bytes; decoding converts bytes to text.

Python
text = "StuyCTF"
raw = text.encode("utf-8")
assert raw == b"StuyCTF"
assert raw.decode("utf-8") == text

print(raw[0])          # 83, an integer
print(raw[:4])         # b'Stuy'
print(raw.hex())       # 53747579435446
print(bytes.fromhex("53747579"))

Integers and endianness

Endianness describes the order of bytes in a multi-byte integer. In big-endian form, the most significant byte comes first. In little-endian form, the least significant byte comes first. Network byte order is big-endian; x86 and x86-64 machines normally use little-endian values in memory.

Python
value = 0x12345678
print(value.to_bytes(4, "big").hex())     # 12345678
print(value.to_bytes(4, "little").hex())  # 78563412

raw = bytes.fromhex("78563412")
print(int.from_bytes(raw, "little"))      # 305419896

Use the struct module for binary layouts

The struct module packs and unpacks C-style binary values. A format prefix such as < selects little-endian and standard sizes; > selects big-endian. Use explicit prefixes so the result does not depend on your computer.

Python
import struct

packet = struct.pack(">HI", 7, 0x12345678)
kind, length = struct.unpack(">HI", packet)

address = 0x4011B6
little_endian_address = struct.pack("<Q", address)

Read and write binary files

Python
from pathlib import Path

data = Path("original/sample.bin").read_bytes()
print(len(data), data[:16].hex())

changed = data.replace(b"OLD", b"NEW")
Path("work/sample.bin").write_bytes(changed)

Write scripts that explain themselves

Use descriptive names, assert assumptions, print intermediate lengths and types, and save the script with the challenge. Accept input from a file or command-line argument when practical. A teammate should be able to run it without editing six hidden constants.

small script pattern
#!/usr/bin/env python3
from pathlib import Path
import sys

def main(path: str) -> None:
    data = Path(path).read_bytes()
    print(f"read {len(data)} bytes")
    print(f"first 16 bytes: {data[:16].hex()}")

if __name__ == "__main__":
    if len(sys.argv) != 2:
        raise SystemExit(f"usage: {sys.argv[0]} FILE")
    main(sys.argv[1])
Practice

Write a program that accepts a hex string, turns it into bytes, prints its length, tries UTF-8 decoding, prints both endian interpretations as an integer, and writes the raw bytes to a file. Test it with valid text, invalid UTF-8, an odd number of hex digits, and an empty string.

Part II

Solving well

Tools matter, but method matters more. These chapters explain how to turn a vague challenge into a sequence of useful questions, how to work with teammates, and how to preserve what you learn.

Chapter 6

A practical solving method

The method is simple: inventory what you have, build a model, test one claim at a time, and keep evidence. The difficult part is noticing when you have stopped doing that and started guessing.

Step 1: Restate the goal

Write the goal in your own words. “Get the flag” is too vague. Better goals include “recover the plaintext from these parameters,” “read the administrator-only object,” or “make execution reach the function named win.” A precise goal tells you what evidence would count as progress.

Step 2: Inventory the givens

Record the prompt, flag format, files, hashes, URLs, credentials, hostnames, ports, source code, hints, point value, and category. Check the actual file types. Make one baseline request to a service. Run a program normally before debugging it. Do not interpret yet; collect facts first.

Step 3: Separate facts from assumptions

StatementFact or assumption?How to verify
“The file is a PNG.”Assumption if based only on .pngUse file and inspect the signature.
“The server returned status 302.”Fact if captured in the responseSave the raw response.
“The cookie contains the user role.”Assumption until decoded or behavior confirms itInspect structure and compare sessions.
“NX is enabled.”Fact if checksec reports it for this binarySave the output and binary hash.

Step 4: Build more than one hypothesis

If a web page says “not authorized,” possible explanations include a role stored in a cookie, a server-side database lookup, a hidden endpoint, or an object-level ownership check. List at least two. The goal is not to be indecisive. It is to avoid falling in love with the first idea.

Step 5: Design a small test

A useful test changes one variable and has an interpretable result. If you change the HTTP method, path, cookie, body, user, and encoding at the same time, you will not know which change mattered. If you run five extraction tools at once, you may lose the chain of evidence.

Step 6: Update the model

After each test, write one sentence: “Because I observed X, I now believe Y.” If the result does not distinguish your hypotheses, the test was not informative. Design a better one.

How to get unstuck

  1. Re-read the title, prompt, attachments, and flag format.
  2. Return to a known baseline and confirm the service or file has not changed.
  3. List what is proven, what is assumed, and what remains unknown.
  4. Explain the challenge to a teammate without using the word “just.”
  5. Search documentation for the concept or tool, not for the exact challenge answer.
  6. Open a hint after writing what you expect the hint to clarify.
  7. Time-box the problem and leave a handoff before switching.
A good next move teaches you something

When choosing between two actions, prefer the one whose result will narrow the problem even if it fails. Random payloads sometimes work, but they teach very little and are hard to reproduce.

Chapter 7

Working as a team

A team gains speed by sharing state, not by placing several people silently on the same problem. Clear claims and handoffs prevent repeated work.

Claim challenges visibly

A useful claim includes the challenge, solver, time, current direction, and next update. For example:

team message
[WEB-200 / Cookie Jar]
Claimed by Ibrahim at 10:12
First pass: compare guest and user sessions; map /api routes
Next update by 10:32

This gives teammates enough information to avoid duplication without turning communication into a burden.

Use roles lightly

It helps to know who is comfortable with web, crypto, forensics, reversing, and pwn, but do not trap people inside a category. Pair newer members with experienced ones. During a long event, one person can watch the scoreboard and claims, but that role should not become a gatekeeper.

Parallelize questions, not confusion

Two people can work on the same challenge if their tasks are clearly separated: one maps endpoints while another reads source; one derives the math while another writes a verification script. If both are trying random inputs, the second person adds little.

Ask for help with context

“I am stuck” forces the next person to restart. A strong request includes:

  • The goal and challenge artifacts.
  • Your current model.
  • The two or three most meaningful observations.
  • What you tested and ruled out.
  • The exact question you want help answering.

Handle flags carefully

Confirm the event's collaboration rules. Submit through the official interface. Do not paste flags into public chats, screenshots, repositories, or livestreams. Record which challenge was solved and who contributed, but avoid turning credit into a competition within the team.

After the event

Hold a short review. Ask which habits saved time, which setup problems repeated, where handoffs failed, and which concepts deserve a workshop. Update this guide with reusable lessons, not challenge-specific flags.

Chapter 8

Notes, handoffs, and write-ups

Notes are working memory for you and your team. A write-up is a teaching document. They are related, but they are not the same thing.

Working notes

Keep the notes chronological. Copy exact commands and meaningful output. Record failed approaches when the failure rules something out. Save raw requests, scripts, hashes, and small artifacts. Do not rely on terminal history; it omits your reasoning and may be lost.

notes template
# Challenge name

## Goal
What must be recovered, reached, or explained?

## Given
Files, hashes, URL, host, port, credentials, flag format.

## Observations
- 10:14: `file sample` reports ELF 64-bit, dynamically linked.
- 10:16: `checksec` shows NX and PIE; no canary.

## Hypotheses and tests
1. Hypothesis:
   Test:
   Result:
   Conclusion:

## Current state
What is known, unknown, ruled out, and worth trying next?

A handoff

A handoff is shorter than the full notes. It should let another teammate continue in a few minutes. Include paths to the original files and scripts, any session state, and one recommended next test.

A write-up

A useful write-up has a clear narrative:

  1. Summarize the problem and important givens.
  2. Explain the key concept before showing commands.
  3. Describe the observation that suggested the solution.
  4. Show the minimal reproducible steps.
  5. Explain why the steps work.
  6. Include one lesson that transfers to a different challenge.
  7. For security bugs, mention the defensive principle that would prevent the issue.

Common write-up problems

  • Command dump: readers see what you typed but not why.
  • Magic jump: the key inference is replaced by “I noticed” or “obviously.”
  • Unreproducible environment: versions, files, offsets, or arguments are missing.
  • Flag leakage: a platform prohibits public solutions or the event is still active.
  • Tool worship: the write-up names a tool without explaining the underlying format or weakness.
Practice

Choose a challenge you solved last month. Give only your notes and files to a teammate who has not seen it. Watch where they become confused. Revise the write-up until they can explain both the solution and the underlying idea.

Part III

Web challenges

Web challenges reward careful comparison. Learn what the browser sends, what the server decides, and where the application trusts data that a user can control.

Chapter 9

HTTP from the ground up

A web application is a conversation made of requests and responses. Browser pages are convenient views of that conversation, but the raw messages are usually easier to reason about.

The shape of a request

raw HTTP request
POST /login?next=%2Faccount HTTP/1.1
Host: challenge.example
Content-Type: application/x-www-form-urlencoded
Cookie: session=abc123
Content-Length: 29

username=alice&password=test

The first line contains a method, request target, and protocol version. Headers provide metadata. A blank line separates headers from the optional body. In this example, the query string controls where the application goes next, the cookie carries session state, and the body contains form data.

Methods

GET normally retrieves a resource. POST often submits data or starts an action. PUT and PATCH commonly update resources, while DELETE removes one. These are conventions, not access controls. A server must authorize every action regardless of the method.

Status codes

RangeMeaningQuestions to ask
2xxThe server handled the request successfully.Did the body contain the expected object? Did state change?
3xxThe client is being redirected or told to use cached content.What is the Location? Does the original response already reveal data?
4xxThe request is invalid, unauthenticated, forbidden, or missing.Does changing user, method, path, or content type change the result?
5xxThe server failed while processing the request.What input triggered the error? Did the response reveal a framework, query, or path?

A status code is one piece of evidence. Compare body length, headers, timing, and application state too. Some challenge applications return 200 OK with an error message inside the page.

URLs and encoding

A URL can include a scheme, host, port, path, query, and fragment. The fragment after # normally stays in the browser and is not sent in an HTTP request. Percent-encoding represents bytes using %HH. Encoding a character does not make it safe; servers may decode data more than once or normalize paths differently.

Cookies and sessions

A cookie is a name-value pair the browser stores and sends according to domain, path, expiration, and security rules. A session cookie often contains an opaque identifier that the server looks up. It may instead contain signed or encrypted data. Decode a structured cookie only to understand it; modifying a value is useful only if you understand how integrity is checked.

  • Secure asks the browser to send the cookie only over secure connections.
  • HttpOnly prevents ordinary JavaScript from reading it.
  • SameSite changes when it is sent with cross-site requests.
  • None of these attributes replaces server-side authorization.

Inspecting requests

Browser developer tools show the network timeline, source, storage, and JavaScript console. An intercepting proxy lets you pause, edit, repeat, and compare requests. Curl is useful when you want a short, reproducible command.

curl examples
curl -i https://challenge.example/
curl -i -L https://challenge.example/              # follow redirects
curl -i -c cookies.txt -b cookies.txt URL           # save and resend cookies
curl -i -X POST -H 'Content-Type: application/json' \
  --data '{"name":"alice"}' URL
curl -sS -D response-headers.txt -o response-body.bin URL
Practice

Use developer tools on a local practice application. Find one request that loads HTML, one that loads JavaScript, and one API request. For each, record the method, path, important headers, body format, status code, response content type, and the browser action that caused it.

Chapter 10

Mapping a web application

Before looking for a weakness, learn the application's vocabulary: its pages, APIs, inputs, roles, objects, and state changes.

Begin with ordinary use

Browse every visible page. Create an account if the challenge allows it. Use each form once with normal values. Watch the requests. Record IDs, object names, roles, and endpoints. A baseline tells you how the application is supposed to behave and gives you something to compare against.

Inspect what the server sends to the browser

  • HTML comments, hidden fields, disabled controls, and linked resources.
  • JavaScript files, route names, API base URLs, and source maps.
  • Cookies, local storage, session storage, and indexed data.
  • Response headers, error messages, framework signatures, and redirects.
  • robots.txt, sitemap.xml, manifests, and well-known paths mentioned by the challenge.

Do not assume a hidden or disabled control is protected. Browser controls are user interface choices. The server must enforce the rule.

Build an endpoint table

Method and pathInputAuthenticationObserved behavior
GET /api/profile/7Path IDSession cookieReturns profile JSON
POST /api/profile/7JSON bodySession cookieUpdates display name
GET /adminNoneUnknown302 to login as guest

The table makes gaps visible. Does an endpoint enforce ownership? Does an update accept fields the interface never shows? Does a different method behave differently?

Content discovery

Automated path discovery can be useful when the rules permit it, but begin with clues from the application. Wordlists generate many requests and often return false positives when custom error pages always have the same status. Compare status, response length, title, and body. Rate-limit yourself and stay on the provided host.

Read source code as a data-flow map

If source is provided, follow user-controlled input from entry point to sensitive operation. Mark transformations and validations. Look for database calls, filesystem paths, template rendering, shell commands, deserialization, authentication checks, and access decisions. Look beyond the string flag and work out how the program reaches it.

Do not skip the boring page

The account settings page, password reset flow, export button, or forgotten API version often matters more than the landing page. Mapping is deliberately slow at first because it prevents hours of random testing later.

Chapter 11

Authentication, sessions, and access control

Authentication asks who you are. Session management connects later requests to that identity. Authorization asks whether that identity may perform this action on this object.

Keep the three questions separate

A user may be correctly authenticated but improperly authorized to read another user's record. A session token may be strong while a password reset flow is weak. An administrator page may be hidden but still reachable. Name the control you are testing.

Build a two-user test

When a challenge allows accounts, create two ordinary users. Have each create a different object. Capture requests for reading, editing, and deleting those objects. Then repeat one user's request with the other user's session while changing only the object identifier.

Object identifiers

Identifiers can appear in paths, query strings, JSON bodies, GraphQL variables, filenames, and hidden fields. Replacing an integer ID is the obvious test, but identifiers can also be UUIDs, usernames, slugs, timestamps, or nested object references. An unguessable identifier reduces guessing; it does not replace authorization.

Role and function checks

Applications should enforce roles on the server for each privileged action. Test the action directly, not only the navigation link. Compare an ordinary user's request with an administrator's request if the lab provides both. Pay attention to extra JSON fields such as role, isAdmin, or ownerId that the client sends back.

Password and account recovery flows

In a legal lab, inspect how reset tokens are generated, delivered, bound to users, expired, and invalidated. Look for user-controlled hostnames in reset links, predictable tokens, responses that reveal whether an account exists, and reset steps that can be skipped. Avoid brute force unless the challenge explicitly expects it and provides a safe rate limit.

Signed tokens

JSON Web Tokens commonly contain a header, payload, and signature separated by dots. Base64url-decoding the header and payload does not break the token; those sections are designed to be readable. Security depends on correct signature verification, algorithm handling, key management, claim validation, and appropriate expiration.

Questions to ask

  • Which server-side decision protects this object or action?
  • What changes when I use a different valid user?
  • Is authorization checked for every method and representation?

Chapter 12

Injection problems

Injection happens when an application intends to handle input as data but an interpreter treats some of it as syntax. The interpreter might be a database, shell, template engine, or query language.

The data-and-code boundary

Suppose code constructs a query by joining strings:

unsafe idea
query = "SELECT * FROM users WHERE name = '" + username + "'"

The programmer wants username to be data. But the database receives one complete string and parses it as query syntax. A quote inside the input may end the intended string literal and change the query. Parameterized queries fix the boundary by sending the query structure and values separately.

How to test systematically

  1. Find an input that reaches an interpreter. Use source, errors, or behavior.
  2. Establish a baseline with ordinary input.
  3. Introduce the smallest syntax character likely to matter.
  4. Compare status, body, timing, and application state.
  5. Determine the context: quoted string, number, JSON operator, shell argument, template expression, and so on.
  6. Build a minimal proof inside the challenge rather than immediately running an automated extractor.

SQL injection concepts

Different SQL contexts support different tests. A condition may influence which rows are selected, a union may append compatible results, an error may reveal information, or a time delay may act as a yes/no signal. Database type, column count, data types, query structure, and result rendering all matter.

Do not memorize one login-bypass string and assume it fits every query. First determine whether input is inside quotes, whether comments are supported, whether the result is visible, and whether the application makes one query or several.

OS command injection

A shell gives special meaning to separators, substitutions, redirects, and expansions. Code that builds a command string from user data may accidentally allow a second command or modified argument. Safer code avoids a shell, passes an argument list to a specific executable, validates allowable values, and runs with minimal privilege.

Template injection

Server-side templates combine data with a template language. If user input becomes template source rather than a template value, expressions may be evaluated. Identify the engine through syntax, errors, source, or framework clues. Start with harmless arithmetic in the lab. The goal of the first test is to prove evaluation, not to jump directly to operating-system access.

NoSQL and structured-query injection

JSON-based APIs may pass objects to database query builders. A parameter expected to be a string may arrive as an object containing operators. Content type, parser behavior, and server-side schema validation determine whether the shape is accepted. Compare a string, array, object, null, boolean, and number only where the challenge allows it, and change one representation at a time.

Automated injection tools are not a first step.

They can generate large request volumes and obscure the underlying context. Use them only on an authorized lab, when the rules allow automation, and after you understand the input and have saved a reproducible request.

Chapter 13

Browser-side security problems

Browsers execute code, store credentials, enforce origin rules, and send authenticated requests. Client-side challenges make sense once you understand which origin owns the page and which context receives the data.

The same-origin policy

An origin is primarily the combination of scheme, host, and port. The same-origin policy limits how a document or script from one origin reads data from another. It does not stop all cross-origin requests, and it does not prevent a user's browser from sending cookies in every circumstance. CORS is a server-controlled way to relax some read restrictions; it is not an authentication system.

Cross-site scripting

XSS occurs when attacker-controlled data becomes executable script in another user's browser. The important question is the output context:

  • Text between HTML elements.
  • An HTML attribute, quoted or unquoted.
  • A JavaScript string, template literal, or code block.
  • A URL or CSS value.
  • A DOM operation such as assigning to innerHTML.

Each context has different parsing rules. A string that closes an HTML element may be harmless inside a text-only DOM property. Start by identifying the source of data, the sink that inserts it, and any transformations between them.

Reflected, stored, and DOM-based cases

Reflected input appears in the immediate response. Stored input is saved and later shown to users. DOM-based XSS happens when client-side JavaScript reads attacker-influenced data and sends it to an unsafe sink. These descriptions tell you where to trace the data, not how severe the result is.

Cross-site request forgery

CSRF tricks a browser into making a state-changing request with the user's ambient credentials. A good defense uses unpredictable tokens bound to the session, appropriate SameSite cookies, origin checks where suitable, and request designs that do not treat simple cross-site submissions as authorization. In a lab, determine whether a state-changing action requires a token and whether the server validates it.

Client-side logic

JavaScript may contain hidden routes, hard-coded data, challenge checks, feature flags, or transformations. Format and search minified code, set breakpoints, and follow values through functions. Remember that client-side restrictions can be changed by the user; real secrets and permissions must live on the server.

Practice

In a deliberately vulnerable web lab, trace one value from URL or form input to its final DOM location. Write down every decoding, sanitization, and assignment step. Explain why a safe text assignment and an HTML-parsing assignment behave differently.

Chapter 14

Files, paths, uploads, and server-side requests

Many web challenges involve an application turning user input into a filename, path, archive entry, URL, or parser instruction. Normalization and validation order are central.

Path traversal

A vulnerable application joins a user-controlled name to a base directory but fails to ensure that the final normalized path remains inside that directory. Parent-directory components, absolute paths, alternate separators, percent-encoding, double-decoding, and platform differences can affect the result.

When source is available, identify when decoding occurs, how paths are joined, whether symbolic links matter, and whether the final canonical path is checked. A safer design maps opaque identifiers to server-selected files or verifies the canonical result against an allowed base directory.

File upload

An upload feature crosses several trust boundaries. Ask:

  • How does the server choose the stored filename and directory?
  • Does it trust the extension, MIME type, magic bytes, or image decoder?
  • Can the file be retrieved, interpreted, or executed?
  • Can one upload overwrite another file?
  • Are archives extracted safely?

A mismatch between extension and content is a clue, not automatically an exploit. Trace the entire lifecycle from upload to storage to later use.

Server-side request forgery

SSRF occurs when the server makes a request to a location influenced by the user. The server may reach internal services, use trusted network position, or expose response data. URL parsing is complicated: redirects, alternate IP representations, DNS changes, schemes, credentials, and validation order can all matter. In a CTF, map what part of the URL you control and what response information comes back.

XML external entities

Some XML parsers can resolve external entities that reference files or URLs. Modern secure configurations generally disable dangerous external resolution. If a challenge accepts XML, determine the parser and configuration, whether a document type is allowed, and where parsed values appear. Treat parser errors as evidence.

Open redirects

An open redirect lets user input choose a redirect destination. By itself it often has limited CTF impact, but it can become important in authentication flows, allowlists, or server-side fetches. Compare absolute URLs, relative paths, encoded values, and parser interpretations only within the challenge.

Normalization is a process

Write the steps in order: URL-decode, split path, join base directory, resolve parent components, check extension, open file. A validation that looks correct in isolation may happen before a later transformation changes the value.

Chapter 15

APIs and modern web applications

Single-page applications often put most visible behavior in JavaScript and exchange structured data with APIs. The core questions remain the same: what input is accepted, what state is trusted, and what authorization is enforced?

REST-style APIs

Map resources, methods, versions, and representations. Test the same action through JSON, form data, or alternate API versions only if the application supports them. Look for object-level authorization, unfiltered fields, unsafe defaults, and differences between create and update operations.

Mass assignment

Frameworks can automatically copy request fields into an object. If the server fails to allowlist editable fields, a client may set properties such as role, balance, owner, approval state, or internal flags. Compare the fields returned by a read endpoint with those submitted by the official client. Then add one plausible field at a time in the lab and observe whether it is ignored, rejected, or stored.

GraphQL

GraphQL exposes a typed query system through one or a few endpoints. Schema introspection may reveal types and fields when enabled. Authorization still belongs in resolvers and data access; hiding a field from the client query does not protect it. Study queries, mutations, variables, aliases, nested relationships, and error messages.

WebSockets

A WebSocket begins as an HTTP upgrade and becomes a long-lived message channel. Capture the handshake, note authentication, inspect message formats, and test whether authorization is enforced for each action. Do not assume the connection's existence proves every message is allowed.

Business logic

Logic flaws violate the intended process without necessarily using special syntax. Examples include applying a discount repeatedly, skipping a required step, using a negative quantity, redeeming the same token twice, or performing actions in an unexpected order. Draw the expected state machine. Then look for missing transitions, repeated transitions, values outside normal ranges, and assumptions the client is expected to enforce.

Race conditions

A race appears when correctness depends on timing between operations. Two requests may both check a balance or one-time token before either updates it. First prove the normal sequential behavior. Then use a small, controlled number of synchronized requests in the lab and confirm the final state. Avoid uncontrolled request floods.

A web challenge closing checklist

  • Did I map all visible pages, API routes, methods, and roles?
  • Did I compare at least two valid users and two owned objects?
  • Did I inspect source, JavaScript, network traffic, cookies, and storage?
  • Did I test server behavior rather than relying on hidden buttons?
  • Did I change one part of each request at a time?
  • Can I explain the vulnerable trust decision in one sentence?

Part IV

Cryptography

Crypto challenges become manageable when you keep representations straight, write down the mathematical assumptions, and test each transformation with a small script.

Chapter 16

Representations, encodings, and data formats

Many beginner “crypto” problems are really representation problems. Before looking for a key, determine whether the data was encrypted, encoded, compressed, serialized, or simply displayed in another base.

Encoding is not encryption

An encoding defines how information is represented. Anyone who knows the encoding can reverse it. Encryption uses a secret key, or a private key paired with a public key, to restrict who can recover the plaintext. Compression removes redundancy. Hashing maps input to a fixed-size digest and is normally designed not to be reversed.

Hexadecimal

Hex uses sixteen symbols. One hex digit represents four bits, so two hex digits represent one byte. A valid byte string therefore usually has an even number of hex digits. Hex is common in hashes, addresses, packet dumps, machine code, and binary formats.

Python
hex_text = "48656c6c6f"
raw = bytes.fromhex(hex_text)
print(raw)                    # b'Hello'
print(raw.hex())              # 48656c6c6f
print(int("ff", 16))          # 255
print(format(255, "08b"))     # 11111111

Base64

Base64 represents three input bytes as four characters. The alphabet usually contains uppercase letters, lowercase letters, digits, +, and /, with = padding. URL-safe Base64 replaces the last two symbols with - and _. The visual pattern is a clue, not proof.

Python
import base64

raw = base64.b64decode("U3R1eXZlc2FudA==", validate=True)
print(raw.decode())

part = "eyJyb2xlIjoic3R1ZGVudCJ9"
part += "=" * (-len(part) % 4)
print(base64.urlsafe_b64decode(part))

Character encodings

ASCII assigns numbers to a small set of English characters and controls. UTF-8 represents Unicode characters using one to four bytes and is compatible with ASCII for the first 128 values. If decoding fails, do not discard the bytes. Inspect them. They may use another encoding or may not be text at all.

Recognizing layers

After each decoding step, ask what the output is. Use file, examine the first bytes, measure entropy, and look for format signatures. Repeated Base64-decoding is appropriate only if each result is valid Base64 and the challenge gives a reason to expect layers. Blindly applying every CyberChef operation can destroy context.

Chapter 17

Classical ciphers

Classical ciphers are useful training because their patterns are visible. They teach you to use language structure, known plaintext, and key constraints as evidence.

Caesar and rotation ciphers

A Caesar cipher shifts each letter by the same amount. There are only 26 possible shifts for English letters, so test all of them. Keep punctuation and case unchanged unless the challenge says otherwise.

Python
import string

def rotate(text, shift):
    lower = string.ascii_lowercase
    upper = string.ascii_uppercase
    out = []
    for ch in text:
        alphabet = lower if ch in lower else upper if ch in upper else None
        if alphabet is None:
            out.append(ch)
        else:
            out.append(alphabet[(alphabet.index(ch) - shift) % 26])
    return "".join(out)

for shift in range(26):
    print(shift, rotate(ciphertext, shift))

Monoalphabetic substitution

Each plaintext letter maps to one ciphertext letter. Letter frequency helps, but short messages vary. Repeated-letter patterns, word lengths, punctuation, common digrams, known flag syntax, and cribs are stronger when combined. A substitution preserves equality: if the first and third ciphertext letters match, the corresponding plaintext letters must also match.

Vigenère and repeating shifts

Vigenère uses a repeating sequence of shifts. The key length creates periodic structure. Repeated ciphertext sequences, index of coincidence, and per-column frequency analysis can suggest a key length. Once the length is guessed, treat each position modulo the length as a Caesar cipher.

Transposition

A transposition cipher rearranges symbols without replacing them. Character frequencies remain unchanged. Rail fence, columnar transposition, route ciphers, and matrix layouts are common CTF forms. Look for a plausible rectangle size, a key that orders columns, or a hint about routes, rails, grids, or reading direction.

Affine ciphers

An affine cipher maps a letter number x to (a x + b) mod 26. The multiplier a must have an inverse modulo 26, which means gcd(a, 26) = 1. This small constraint leaves few key pairs, so exhaustive testing is reasonable.

Score candidates, but read them too

Language scoring can rank thousands of possibilities, but flags, usernames, code, and short phrases may not resemble ordinary English. Keep the challenge context and expected format in the loop.

Chapter 18

XOR and stream-cipher mistakes

XOR is simple, reversible, and everywhere in CTF cryptography. The operation itself is not weak. Problems come from key reuse, predictable plaintext, short repeating keys, or broken nonce handling.

XOR properties

For each bit, XOR outputs 1 when the inputs differ. It has useful algebraic properties:

  • x XOR 0 = x
  • x XOR x = 0
  • (x XOR k) XOR k = x
  • Order and grouping do not matter.
Python
def xor_bytes(left: bytes, right: bytes) -> bytes:
    if len(left) != len(right):
        raise ValueError("lengths must match")
    return bytes(a ^ b for a, b in zip(left, right))

plaintext = b"hello"
key = bytes.fromhex("1020304050")
ciphertext = xor_bytes(plaintext, key)
assert xor_bytes(ciphertext, key) == plaintext

Single-byte XOR

Only 256 keys exist. Try them all and score outputs by printability, expected flag syntax, or language. Print the key as both an integer and byte. Do not discard non-ASCII output if the expected plaintext is binary.

Repeating-key XOR

A short key repeats across the message. Guess the key length using repeated patterns or normalized Hamming distance, then group bytes by position modulo the key length. Each group is encrypted by one key byte and can be scored like single-byte XOR.

Known plaintext

If you know or strongly suspect plaintext bytes, XOR them with the corresponding ciphertext to recover that portion of the keystream. File headers and flag prefixes make useful cribs. Treat a crib as a hypothesis and validate whether the recovered keystream produces sensible bytes elsewhere.

Keystream reuse

If two messages use the same keystream, then C1 XOR C2 = P1 XOR P2; the key disappears. This does not immediately reveal both plaintexts, but language structure and cribs can recover them together. Modern stream-cipher and counter-mode designs require a unique nonce for each key so the same keystream is never reused.

Practice

Encrypt two English sentences with the same random keystream. Give the ciphertexts to a partner along with one likely word. Have them recover part of both messages and explain why reusing the keystream caused the leak.

Chapter 19

Number theory for CTF cryptography

You do not need advanced mathematics to begin. You do need comfort with remainders, greatest common divisors, modular inverses, and fast exponentiation.

Modular arithmetic

Writing a ≡ b (mod n) means that a and b leave the same remainder when divided by n. You may add and multiply congruences. Division is different: to divide by a, you need a multiplicative inverse of a modulo n.

Greatest common divisor

The Euclidean algorithm computes gcd(a, b). The extended Euclidean algorithm also finds coefficients x and y such that ax + by = gcd(a,b). If the gcd is 1, then x is an inverse of a modulo b.

Python
from math import gcd

assert gcd(17, 3120) == 1
inverse = pow(17, -1, 3120)
assert (17 * inverse) % 3120 == 1

# Modular exponentiation without creating the enormous full power
value = pow(base, exponent, modulus)

Prime numbers and Euler's totient

A prime has exactly two positive divisors. For distinct primes p and q, the totient of n = pq is (p - 1)(q - 1). RSA uses this structure. If you can factor n, you can usually derive the private exponent.

The Chinese remainder theorem

The CRT reconstructs a value from its remainders modulo pairwise coprime moduli. It can speed up RSA operations and appears in attacks where the same message is sent with a small exponent to several different moduli. Write down the exact congruences before reaching for a library.

Integer roots are not floating-point roots

Cryptographic integers can have thousands of bits. Floating-point approximations lose precision. Use an integer-root routine and verify the candidate by raising it back to the power. A correct exact root has zero remainder.

Keep a scratch page

Write the known values, equations, bounds, and required unknown. Many failed crypto solves come from using the right formula with the wrong variable or modulus.

Chapter 20

RSA challenge patterns

Textbook RSA is a mathematical operation, not a complete secure encryption scheme. CTFs usually provide a broken parameter choice, reused value, missing padding, or implementation leak.

The basic construction

  1. Choose large primes p and q, then compute n = pq.
  2. Choose public exponent e coprime to φ(n).
  3. Compute private exponent d = e⁻¹ mod φ(n).
  4. Encrypt integer message m as c = m^e mod n.
  5. Decrypt as m = c^d mod n.
textbook RSA after factoring n
from math import prod

n = p * q
phi = (p - 1) * (q - 1)
d = pow(e, -1, phi)
m = pow(c, d, n)
length = max(1, (m.bit_length() + 7) // 8)
plaintext = m.to_bytes(length, "big")
print(plaintext)

Factorable modulus

If the primes are too small, too close, generated badly, or share a factor with another modulus, factoring becomes practical. Before trying a general-purpose factorizer, compute gcds between provided moduli. A shared prime appears immediately as a nontrivial gcd.

Small public exponent and no padding

If m^e < n, modular reduction never occurs and the ciphertext is the ordinary integer power. An exact integer e-th root recovers m. Proper randomized padding prevents this simple structure from being exposed.

Broadcast and common-modulus situations

Encrypting the same unpadded message with a small exponent under several coprime moduli can allow CRT reconstruction followed by an integer root. Reusing one modulus with different exponents can also be dangerous when the same message is used and the exponents have a favorable relationship. Identify which values are repeated before choosing an attack.

Weak private exponent

If d is unusually small, continued-fraction methods may recover it. Challenge wording about speed, tiny private keys, or unusual key generation may point here. Verify a candidate by checking that encryption and decryption agree.

Padding and oracles

Real RSA encryption uses a padding scheme that encodes randomness and structure. A system that reveals whether a decrypted message has valid padding can become an oracle. These attacks are about adaptive information leakage, not simply “removing padding.” In a CTF, model exactly what yes/no signal the server returns and keep request counts within event rules.

RSA triage

  • List n, e, c, and every repeated or leaked value.
  • Check sizes, gcd relationships, and whether the modulus factors.
  • Determine whether padding is present.
  • Convert between integers and bytes explicitly.
  • Verify the recovered plaintext by re-encrypting when possible.

Chapter 21

Hashes, message authentication, and symmetric encryption

These primitives solve different problems. A hash summarizes data, a MAC authenticates it with a secret, and encryption hides it. Secure systems often need more than one property.

Cryptographic hashes

A cryptographic hash maps arbitrary input to a fixed-length digest. Important goals include resistance to finding a preimage, a second input with the same digest, or any collision. MD5 and SHA-1 have serious collision weaknesses and should not protect modern integrity decisions. In CTFs, they may appear because the challenge intentionally uses weak designs.

Python
import hashlib

data = b"challenge data"
print(hashlib.sha256(data).hexdigest())
print(hashlib.md5(data).hexdigest())      # recognize legacy use; do not choose it

Password hashing

Fast general-purpose hashes are poor password storage because attackers can test guesses quickly. Password-hashing systems use salts and deliberately expensive algorithms. A salt does not need to be secret; it prevents identical passwords from sharing one stored value and defeats precomputed tables.

MACs and signatures

A message authentication code uses a shared secret to provide integrity and authenticity. HMAC is a standard construction built from a hash. A plain hash of secret || message is not a safe substitute and may have structural weaknesses. Digital signatures use a private signing key and a public verification key, which changes who can verify and who can produce a valid signature.

Block ciphers and modes

A block cipher such as AES transforms fixed-size blocks under a key. A mode defines how to encrypt longer messages.

Initialization vectors and nonces

An IV or nonce is not usually a secret. Its required property depends on the construction: unpredictability, uniqueness, or both. Reuse can be catastrophic in stream-like modes. Read the challenge code rather than applying a generic rule.

Padding

Block modes may need a rule for representing a final partial block. PKCS#7 appends N bytes, each with numeric value N. Even a message already aligned to a block receives a full block of padding. A padding oracle exists when an application reveals whether decrypted padding is valid, allowing an attacker to learn plaintext through repeated chosen modifications.

Ask what property failed

Did the design reuse a nonce, omit authentication, expose a validation difference, use a weak key, or confuse encoding with encryption? Naming the failed property is more useful than naming the library.

Part V

Digital forensics

Forensics challenges ask you to reconstruct information from artifacts. Preserve originals, work from broad observations toward narrow ones, and keep a chain of reasoning.

Chapter 22

File triage and containers

A filename is a label. The bytes determine the format. Begin with identification and structure before looking for hidden messages.

A repeatable first pass

terminal
sha256sum sample

xxd -l 128 sample

Each command answers a different question. The hash identifies the artifact. File size and timestamps provide context. file checks signatures. xxd shows the header. ExifTool reads structured metadata. Strings finds printable regions. Binwalk looks for embedded signatures. None of them proves that its interpretation is the challenge solution.

Magic bytes and format structure

Many formats begin with a signature. A PNG starts with an eight-byte signature, a PDF begins with %PDF-, and a ZIP commonly begins with PK bytes. Formats also contain length fields, chunks, central directories, or end markers. Extra bytes after an apparent end may be legitimate, accidental, or deliberately appended.

Archives

List an archive before extracting it. Check filenames, directory traversal components, comments, timestamps, compression methods, encryption flags, and nested containers. Extract into a new empty directory, never over important files.

archive inspection
unzip -l sample.zip
zipinfo -v sample.zip | less
7z l sample.7z
tar -tvf sample.tar
mkdir extracted && 7z x sample.zip -oextracted

Documents

Modern office documents are often ZIP containers holding XML, media, relationships, and metadata. PDFs contain numbered objects, streams, cross-reference data, attachments, JavaScript in some cases, and incremental revisions. Use format-aware tools and inspect the document visually in a safe viewer. Text extraction alone can miss hidden, layered, or encoded content.

Timestamps

Filesystems and formats record different timestamps with different precision and time zones. Creation, modification, metadata-change, and access times are not interchangeable. Copying or extracting a file can change them. Record the source and interpretation of every timestamp before building a timeline.

Extraction changes the system.

Archive entries can contain unsafe paths, symbolic links, enormous decompressed data, or malicious content. Extract challenge files in an isolated workspace and inspect the listing first.

Chapter 23

Images, audio, and steganography

Steganography hides the existence or location of information. In a CTF, the best clue is usually a mismatch between what the file appears to be and what its structure contains.

Image triage

  1. Verify the format and dimensions.
  2. Read metadata and comments.
  3. Check whether the file parses cleanly.
  4. Inspect color channels, alpha, frames, palettes, and unusual dimensions.
  5. Look for appended or embedded files.
  6. Only then test format-appropriate steganography methods.

PNG

PNG is chunk-based. Each chunk has a length, type, data, and checksum. Important chunks include IHDR, one or more IDAT chunks, and IEND. Text chunks, ancillary chunks, invalid checksums, unusual dimensions, or data after IEND may matter. A parser can list chunks more reliably than manually searching the compressed image data.

JPEG

JPEG uses marker segments and lossy compression. Metadata often lives in EXIF or comment segments. Data can be appended after the end marker, but not every extra region is meaningful. LSB techniques that assume raw pixel values do not transfer directly to ordinary JPEG compression.

Least significant bits

Changing the lowest bit of a color channel can make little visible difference while carrying data. But there are many choices: channel order, bit order, pixel traversal, alpha use, number of bit planes, and length encoding. Use challenge clues and statistical or visual channel analysis. If one tool reports hundreds of candidates, you have not finished the reasoning.

Password-based steganography

Tools such as Steghide store encrypted or compressed payloads in supported media. A password may come from the prompt, metadata, another file, or a solved subproblem. Do not begin by brute-forcing every image. First determine whether the format and tool signature make the hypothesis plausible.

Audio

For audio, inspect format, sample rate, channels, duration, metadata, and waveform. Listen at a safe volume. View a spectrogram to see how energy changes over frequency and time. Challenge data may be encoded in tones, Morse-like timing, separate stereo channels, phase, or metadata rather than an audible voice.

common inspection commands

Chapter 24

Packet-capture analysis

A packet capture is a timeline of observed network frames. Start with the shape of the traffic, then narrow to protocols, endpoints, conversations, and content.

Preserve context

Record the capture hash, capture start and end times, interface information when available, and whether packets may be missing. A packet trace is an observation point, not a perfect record of the entire network.

Broad-to-narrow workflow

  1. Open capture-file properties and protocol hierarchy.
  2. List endpoints and conversations.
  3. Identify unusual protocols, ports, traffic volume, or timing.
  4. Apply a display filter for one question.
  5. Follow a TCP or UDP stream.
  6. Export relevant objects or fields.
  7. Return to the full timeline to place the finding in context.

Chapter 25

Disks, memory, logs, and timelines

Larger forensics challenges combine artifacts. The skill is not finding one dramatic string; it is correlating independent evidence into a reliable timeline.

Disk images

A disk image may contain partitions, filesystems, allocated files, deleted directory entries, unallocated space, journals, and slack. Work read-only. Identify partition offsets and filesystem types before mounting or using recovery tools. A deleted file may be partially recoverable if its data blocks were not overwritten.

Memory images

Memory can contain process lists, command lines, loaded modules, network connections, handles, injected regions, decrypted content, and fragments of files. Analysis tools need the correct operating-system context and symbol information. Begin with system identity and process inventory, then move toward the processes relevant to the challenge story.

Logs

Logs are structured claims made by software. They may be incomplete, duplicated, delayed, rotated, tampered with, or recorded in different time zones. Parse fields rather than treating each line as plain prose. Useful questions include who acted, from where, on what object, at what time, with what result, and which event precedes or follows it.

Browser artifacts

Browser profiles may store history, downloads, cookies, caches, local storage, and form data. Many artifacts use SQLite databases or structured cache formats. Work on a copy. A timestamp's epoch and unit may differ by browser and artifact.

Part VI

Reverse engineering

Reverse engineering is the process of learning how a program works from its compiled form and behavior. You are building a useful model, not recreating every line of source code.

Chapter 26

How a compiled program looks at the low level

A processor follows instructions that move data, perform arithmetic, compare values, change control flow, and interact with memory. Assembly is a readable notation for those instructions.

Registers and memory

Registers are small storage locations inside the processor. On x86-64, general-purpose registers include rax, rbx, rcx, rdx, rsi, rdi, rsp, and rbp. The instruction pointer is rip. Subregister names such as eax, ax, and al refer to smaller portions.

Memory is addressed by numbers. A process sees a virtual address space containing code, read-only data, writable global data, heap allocations, shared libraries, and stacks. Exact layouts vary with platform, binary type, and protection settings.

Common instruction families

InstructionTypical meaningQuestion

leaCompute an address expressionIs this a pointer or arithmetic shortcut?
add, sub, imulArithmeticWhat width and signedness?
xor, and, or, shiftsBit operationsIs this masking, clearing, encoding, or arithmetic?
cmp, testSet condition flagsWhich later branch consumes the result?
jz, jne, jl, jaConditional branchIs the comparison signed or unsigned?
call, retFunction call and returnWhere are arguments and return values?

Flags and signedness

A comparison sets processor flags. Different jump instructions interpret those flags as equality, signed order, or unsigned order. The same bit pattern can represent a negative signed integer or a large unsigned integer. When decompiler output looks strange, check the instruction width and branch condition.

Calling conventions

A calling convention defines how functions receive arguments, return values, preserve registers, and use the stack. On common 64-bit Linux systems, early integer or pointer arguments are passed in rdi, rsi, rdx, rcx, r8, and r9, with the return value in rax. Windows x64 uses a different order. Always identify the platform.

The stack

The stack holds return addresses, saved registers, local storage, and spilled values. rsp points near the current top. A function may create a stack frame by adjusting rsp and optionally using rbp as a stable reference. Compiler optimization can remove familiar frame patterns.

Little-endian display

On x86-64, the integer 0x401234 stored in eight bytes appears in memory as 34 12 40 00 00 00 00 00. Debuggers may display the numeric value in normal notation while a hex dump shows byte order. Both can be correct.

Practice

Compile a short C function at no optimization and again at a high optimization level. Disassemble both. Identify arguments, return value, comparison, branch, and function calls. Note which source variables disappear in the optimized version.

Chapter 27

Static analysis

Static analysis studies a program without executing it. Begin with format and metadata, then move toward functions and data that are relevant to the challenge goal.

Identify the binary

Determine architecture, bitness, byte order, executable format, linking, stripping, and interpreter. A stripped binary lacks many helpful symbol names, but code and imports remain.

Start from anchors

Useful anchors include success and failure strings, imported comparison functions, input functions, cryptographic constants, filenames, URLs, and error messages. Follow cross-references from the anchor to the code that uses it. This is usually faster than reading from the entry point line by line.

Use a decompiler carefully

A decompiler proposes higher-level control flow and variables. Rename functions and variables as you learn their roles. Set correct parameter and return types when evidence supports them. But verify important details in disassembly:

  • Signed versus unsigned comparisons.
  • Integer width and truncation.
  • Pointer arithmetic and array indexing.
  • Whether a function returns or tail-calls another.
  • Stack variables merged or split by optimization.

Recover algorithms from data flow

For a password checker, identify input length checks, loops, transformations, and the final comparison. Rewrite the transformation in Python, test it on known inputs, and invert it if possible. Avoid patching the success branch until you understand whether the challenge asks for the actual password or only execution of the success path.

Recognize compiler artifacts

Stack setup, runtime initialization, exception handling, position-independent thunks, standard-library wrappers, and compiler-generated security checks can distract from the challenge logic. Learning common artifacts helps you separate application code from support code.

Rename aggressively, claim cautiously

A name such as check_password is a working hypothesis. Use it because it makes the program easier to discuss, but be willing to change it when new evidence appears.

Chapter 28

Dynamic analysis

Dynamic analysis observes a running program. It answers questions that static analysis leaves uncertain: which branch is taken, what value reaches a comparison, and how memory changes.

Run normally first

Use a disposable environment. Try empty input, a short normal input, a long input, and the format suggested by the prompt. Record output and exit status. Check whether the program reads standard input, command-line arguments, environment variables, or files.

System and library call traces

strace records interactions with the operating system, such as opening files, reading, writing, mapping memory, and making network connections. ltrace can show calls to dynamically linked library functions. A visible strcmp argument may reveal a simple password check, although optimized or custom comparisons will not appear that way.

strace -f -o trace.txt ./challenge
ltrace -o libraries.txt ./challenge
grep -E 'openat|read|write|connect' trace.txt

Debugger basics

nexti executes one instruction while stepping over function calls. stepi enters calls. The x command examines memory; its format controls unit size and presentation. Break immediately before a comparison or branch, inspect operands, predict the outcome, then execute one instruction and verify.

Breakpoints and watchpoints

A breakpoint stops at an instruction or symbol. A conditional breakpoint stops only when an expression is true. A watchpoint stops when a memory location changes. Watchpoints are useful for learning where an output buffer, counter, or state value is modified.

ASLR and PIE

Address-space randomization changes load addresses. A PIE executable can load its code at different bases. Debuggers may change or disable parts of randomization depending on configuration. Prefer symbols and module-relative offsets over copying one absolute address into notes.

Patching

Changing a conditional branch can prove that you found the success gate, but it may not recover the required input. Patch a copy, document the offset and original bytes, and be clear whether patching is part of the intended solve or only a diagnostic experiment.

Practice

Write a short password-check program. Strip it, give it to a partner, and ask them to locate the final comparison statically. Then have them break before the comparison, inspect both values, and explain the result without modifying the branch.

Part VII

Binary exploitation

Binary exploitation uses programming errors to gain control over a program's data or execution. These chapters focus on understanding small CTF binaries in an isolated environment.

Chapter 29

Memory safety and vulnerability primitives

Low-level languages let programs work directly with memory. When a program uses the wrong size, lifetime, or type, input can affect data the programmer did not intend.

Memory has no built-in meaning

Bytes become integers, characters, pointers, instructions, or structures because the program treats them that way. A pointer is an address. If an index or length is wrong, the processor will still access the computed address unless a protection or unmapped page stops it.

From bug to primitive

Finding a crash is only the start. Ask what you can control and how reliably:

  • Can you control the instruction pointer?
  • Can you read from a chosen address?
  • Can you write a chosen value to a chosen address?
  • Can you change an authorization variable or function pointer?
  • Can you leak a code, stack, heap, or library address?

Reproduce before exploiting

Use an isolated challenge environment.

Unknown binaries can perform any action your account can perform. Do not debug them alongside personal files, credentials, or important network access.

Chapter 30

Stack overflows and control flow

A beginner stack challenge often places an input buffer near a saved return address. The solve requires an exact offset, a valid target, correct byte order, and an input path that preserves the payload.

A simplified stack frame

A function may reserve space for local variables, save a previous frame pointer, and store a return address from the caller. If an unsafe read writes past a local buffer, later bytes can overwrite adjacent data. The precise layout comes from the compiled binary, not the source declaration alone.

Find the offset with a cyclic pattern

A cyclic pattern is designed so short subsequences are unique. Feed the pattern, inspect the overwritten value at the crash, and calculate its position. This is more reliable than counting repeated A characters.

pwntools pattern workflow
from pwn import *

print(pattern)

# After observing the overwritten 8-byte value in the debugger:
offset = cyclic_find(observed_value, n=8)
print(offset)

Ret2win

Many teaching binaries contain a function that prints the flag but is never called normally. Once the return-address offset is known, the payload can place that function's address at the saved return location. On 64-bit systems, stack alignment may matter before the called function uses instructions or library code expecting a particular alignment.

Practice

Use a purpose-built ret2win lab. Record the binary protections, input function, cyclic pattern, observed crash value, calculated offset, target symbol, packed address, and final payload length. Explain why each field is necessary.

Chapter 31

Format strings, code reuse, and address leaks

When data is interpreted as a format string, or when non-executable memory prevents injected code, an exploit often relies on information leaks and reuse of code already present.

Format-string bugs

The safe pattern is printf("%s", user_input). The dangerous pattern is printf(user_input), because percent sequences inside the input become instructions to the formatting function. Depending on arguments and platform, a challenge may expose stack values, dereference pointers, or write the number of printed characters through %n.

Begin by finding the input's argument position with harmless reads. Confirm pointer widths and output. For a write, calculate printed counts carefully, account for values already printed, and prefer narrow writes when the target permits them.

GOT and PLT at a high level

Dynamically linked executables use linkage structures to call library functions. The Procedure Linkage Table provides call stubs, while the Global Offset Table holds resolved addresses. A leak of a known library function's runtime address can reveal the loaded library base when you know the exact library build.

Return-oriented programming

ROP chains short instruction sequences ending in ret. Each sequence is called a gadget. By arranging stack values, an exploit can load argument registers and call existing functions. A common educational pattern is:

  1. Use a first chain to print or send a function address from memory.
  2. Return to a stable function so the program accepts a second input.
  3. Calculate the library base from the leak.
  4. Build a second chain using addresses from that exact library.

Leaks and base calculations

If a leaked address is the runtime address of a known symbol, subtract the symbol's file offset to obtain the module base. Then add offsets for other symbols or strings. Verify that the result is page-aligned where expected and that the remote library matches your local copy.

calculation pattern
leaked_puts = unpacked_value
libc.address = leaked_puts - libc.sym["puts"]
system = libc.sym["system"]
bin_sh = next(libc.search(b"/bin/sh\x00"))

log.info(f"libc base: {libc.address:#x}")
log.info(f"system: {system:#x}")

Gadget side effects

A gadget may pop additional registers, adjust the stack, or depend on alignment. Read the full sequence. In x86-64 System V code, a lone ret gadget is sometimes added to restore 16-byte stack alignment before a library call.

A chain is a program

Write the chain as pseudocode first: “load first argument, call puts on GOT entry, return to main.” Then translate each step into gadgets and words. This is much easier to debug than copying a long list of addresses.

Chapter 32

Building reliable exploit scripts

A good exploit script records assumptions, works locally and remotely, and fails with useful information. Reliability is part of the solve.

A small pwntools structure

Python / pwntools
#!/usr/bin/env python3
from pwn import *

exe = context.binary = ELF("./challenge", checksec=False)
context.log_level = "info"

def start():
    if args.REMOTE:
        return remote(args.HOST, int(args.PORT))
    if args.GDB:
        return gdb.debug([exe.path], gdbscript="break main\ncontinue")
    return process([exe.path])

io = start()

offset = 72
payload = flat(
    b"A" * offset,
    exe.sym["win"],
)

io.sendlineafter(b"> ", payload)
io.interactive()

Use byte strings

Network and process data is bytes. Keep prompts, payloads, delimiters, and responses as bytes. Encode human text explicitly. Mixing str and bytes creates fragile conversions and warnings.

Synchronize with the program

Use sendlineafter, recvuntil, or explicit parsing instead of arbitrary sleep calls. Save received data when debugging. A remote service can respond more slowly or split output differently from a local process.

Pack addresses correctly

Pwntools uses the selected context to pack integers. On a 64-bit little-endian binary, p64 packs eight bytes. The flat helper combines byte strings and integers. Still print payload length and a hex view when debugging.

Separate stages

Write functions such as leak_address(), calculate_base(), and send_second_stage(). Assert that leaks have plausible lengths and bases. A failed first stage should stop before the script builds nonsense addresses.

Local and remote differences

  • Different libc or loader versions.
  • Network buffering and line endings.
  • Environment variables and working directory.
  • ASLR behavior and timeouts.
  • Proof-of-work or menu wrappers.

Final reliability checklist

  • Does the script begin from a fresh process and solve repeatedly?
  • Are the binary, library, and loader hashes recorded?
  • Are offsets derived or clearly documented?
  • Does parsing tolerate normal variation without accepting nonsense?
  • Can a teammate run it from the notes?
  • Does it stay within the event's connection and automation rules?

Part VIII

Other common categories

Some challenges do not fit neatly into the major technical categories. The same habits still apply: define the question, preserve sources, model the data, and write a small test.

Chapter 33

Open-source intelligence

OSINT is disciplined research using information available to the public. A strong solve is a documented chain from clue to source to conclusion, not a lucky search result.

Define the exact research question

“Find this person” is broad and invites irrelevant collection. Better questions are “Which city is shown in this challenge image?” or “What year did the organization use this logo?” Write the minimum fact required for the flag. This keeps research focused and reduces unnecessary exposure of personal information.

Extract clues before searching

Transcribe visible text, signs, usernames, dates, file names, domain fragments, architectural details, road markings, languages, weather, shadows, transit symbols, and image metadata. Separate direct observations from interpretations. “The sign contains the letters ST” is an observation; “this is a school in New York” is a hypothesis.

Search in layers

  1. Search the most distinctive exact phrase in quotation marks.
  2. Add one contextual term such as city, organization, date, or file type.
  3. Try spelling, transliteration, abbreviation, and date variants.
  4. Search official sources, archives, maps, code repositories, or domain records as appropriate.
  5. Record both useful and misleading results.

Source quality

Prefer a primary source that directly supports the claim: an official record, original photograph, authoritative map, project repository, archived organization page, or document from the relevant institution. Search snippets and reposted images are leads, not strong evidence. Preserve the URL, access time, page title, and exact fact supported.

Archived and changing pages

Web pages change. An archive can show earlier versions, but archive dates describe capture time, not necessarily publication time. Compare multiple captures and corroborate with dated records. Note missing assets, redirects, and the possibility that a page was never archived.

Geolocation

Use several independent features: road signs, lane markings, driving side, utility poles, terrain, vegetation, architecture, transit, sun direction, business names, and language. Avoid deciding from one generic feature. When comparing maps or street imagery, match fixed relationships such as intersections and building shapes rather than temporary vehicles.

Usernames and identities

A matching username does not prove the same person. Look for corroborating dates, writing style, linked accounts, project names, profile images, or public self-identification. Keep the work limited to what the challenge requires. Do not contact people, access private accounts, evade privacy controls, or publish unrelated personal information.

Do not turn a puzzle into surveillance.

Use public sources, collect the minimum relevant facts, and stop when the challenge question is answered. Never harass, impersonate, contact, or dox a real person.

Practice

Choose a public photograph of a well-known landmark. Remove the obvious landmark from the crop. Ask a partner to identify the city using at least three independent clues and two sources. Their write-up should distinguish observations, hypotheses, and verification.

Chapter 34

Password hashes and offline guessing

Some CTFs provide a password hash and ask you to recover a weak password. This is an offline search problem inside the challenge, not permission to attack real accounts.

Identify the representation carefully

Length and alphabet can suggest a hash, but many formats look alike. Context, prefixes, separators, and tool identification can help. A string may contain the algorithm, cost, salt, and digest together. Do not strip fields until you understand the format.

Why salts matter

A salt is a unique value combined with the password before hashing. It prevents users with the same password from sharing the same stored hash and makes precomputed tables ineffective across salts. The salt is normally stored with the hash. It does not make a weak password strong; each candidate can still be tested for that one salt.

Choose guesses from the challenge

Start with context: a supplied wordlist, known password policy, username, theme, dates, or source code. Generic giant lists are not always efficient. Rule-based mutations model common changes such as capitalization, suffix digits, and character substitutions. Mask attacks are appropriate when the pattern is known, such as a fixed prefix followed by four digits.

Verify independently

When a tool reports a candidate, recompute the hash using the correct algorithm, salt, and parameters. Then test it only against the challenge service if required. Keep the recovered challenge password out of public notes while the event is active.

John and Hashcat workflow

Defensive lesson

Applications should use a modern password-hashing scheme with a unique salt and an appropriate work factor, support strong passphrases, protect reset flows, rate-limit online attempts, and offer multi-factor authentication where appropriate. Offline challenge speed is a reminder that database compromise changes the problem.

Offline challenge hashes only.

Do not collect hashes from real systems or attempt recovered passwords against other accounts. Password reuse makes that especially harmful and unauthorized.

Chapter 35

Miscellaneous challenge patterns

Miscellaneous challenges often test whether you can recognize a data structure, automate a repetitive task, or read a small program carefully.

Repeated transformations

If a challenge repeats a reversible operation hundreds of times, write a loop. First reproduce one step by hand and test your function against it. Then automate. Save intermediate values every so often so you can identify where a long pipeline goes wrong.

Interactive arithmetic and parsing

Some services ask many quick questions. Read until a stable delimiter, parse the expression or data, compute the answer, and send it. Do not use Python's unrestricted eval on remote input. Parse the expected grammar or allowlist operators.

safe arithmetic idea
import operator

OPS = {"+": operator.add, "-": operator.sub, "*": operator.mul}

def calculate(left: str, op: str, right: str) -> int:
    if op not in OPS:
        raise ValueError("unsupported operator")
    return OPS[op](int(left), int(right))

QR codes and barcodes

Verify the symbology, correct perspective and contrast if necessary, and decode with more than one tool when the result is uncertain. A decoded string may be another encoding, URL, or binary payload. Keep the image transformation steps reproducible.

Git history

A repository contains commits, branches, tags, references, and objects beyond the current files. Look at the log, diffs, removed files, unmerged branches, and reflog if included. Secrets deleted from the latest commit may remain in earlier objects.

Containers and deployment files

Dockerfiles, compose files, environment templates, CI configuration, and deployment manifests reveal ports, files, commands, users, build stages, and secrets intended for the challenge. Distinguish build-time data from runtime data. Inspect image layers in an authorized artifact because a file deleted in a later layer can remain in an earlier one.

Esoteric languages and virtual machines

Identify the instruction set and state: tape, stack, registers, memory, input, and output. Trace a short prefix manually. Then write or adapt an interpreter with logging. A challenge-specific virtual machine is often simpler than it first appears once you write each opcode in plain language.

Constraint and logic problems

Translate conditions into variables and equations. Solve small cases by hand to validate the model. Brute force is reasonable when the search space is bounded; pruning and constraint solvers help when relationships are structured. Always verify the candidate in the original checker.

Misc does not mean random

The prompt usually contains a clue about the representation or process. Name the state, transition, and stopping condition before reaching for a large script.

Guided lab: following data through the shell

The purpose of this lab is to make pipelines feel concrete. Learners should finish able to explain where data comes from, where it goes, and why each program belongs in the chain.

Preparation

Create a directory containing twenty small files. Use several extensions, include one filename with spaces, place one file in a hidden directory, compress a nested directory, and put a line such as meeting-code: blue-orchid in one text file. Add a binary file containing printable strings and give one archive a misleading extension. Do not include executable malware.

Student goal

Find the meeting code, identify the misleading file, and produce a short note that another person can reproduce from a clean copy.

Suggested sequence

  1. Use pwd and find to inventory the workspace without opening files one by one.
  2. Use file on every file and compare the result with each extension.
  3. List the archive before extracting it.
  4. Search ordinary text recursively while excluding binary noise.
  5. Use strings only on files that are not plain text.
  6. Combine results with sort, uniq, or tee.

Questions for the room

  • What is the difference between a filename and a file format?
  • Why can an unquoted filename with spaces break a loop?
  • When should output go to less, a file, or another command?
  • Why is recursively running strings over everything a poor first step?
  • Which command produced evidence, and which command only presented it differently?

Add duplicate lines and ask learners to count unique values. Add timestamps and ask them to find files newer than a reference file. The final note should include the starting directory hash or archive hash, exact commands, relevant output, the recovered meeting code, and one paragraph explaining how the file-format mismatch was detected. A screenshot without commands is not enough.

Chapter 40

Guided lab: writing a small binary parser

This lab teaches learners to replace guesswork with an explicit binary layout. It also reinforces byte strings, endianness, lengths, and defensive parsing.

A simple made-up format

Prepare several files with this layout: four ASCII magic bytes STUY, one version byte, one flags byte, a two-byte big-endian payload length, the payload, and a four-byte checksum. Include one valid file, one with the wrong magic, one truncated file, one with an impossible length, and one with a bad checksum.

Development steps

  1. Read the entire file as bytes and print its length and first sixteen bytes in hex.
  2. Check the magic before parsing later fields.
  3. Read version and flags as integers.
  4. Use int.from_bytes or struct.unpack for the length.
  5. Check that the claimed payload fits before slicing.
  6. Compute the checksum using the exact stated rule.
  7. Print a structured summary and a clear error for invalid files.
parser outline
from dataclasses import dataclass
from pathlib import Path
import struct

@dataclass
class Record:
    version: int
    flags: int
    payload: bytes

def parse(data: bytes) -> Record:
    if len(data) < 12:
        raise ValueError("file is too short")
    if data[:4] != b"STUY":
        raise ValueError("wrong magic")
    version, flags, length = struct.unpack(">BBH", data[4:8])
    end = 8 + length
    if end + 4 != len(data):
        raise ValueError("length does not match file size")
    payload = data[8:end]
    stored_checksum = struct.unpack(">I", data[end:end + 4])[0]
    # Replace this with the checksum rule supplied by the lab.
    calculated = sum(data[:end]) & 0xffffffff
    if stored_checksum != calculated:
        raise ValueError("checksum mismatch")
    return Record(version, flags, payload)

Teaching points

The parser checks structure before trusting values. A length field is untrusted data. A slice silently returning fewer bytes can hide truncation, so validate boundaries explicitly. The checksum detects accidental or intentional changes according to the exercise, but a simple sum is not cryptographic authentication.

Extensions

Add multiple records, optional sections controlled by flag bits, UTF-8 text that may fail decoding, or a compressed payload. Ask learners to write unit tests for every invalid sample. Have one pair create a file generator and another pair write the parser from the format specification.

Chapter 42

Guided lab: testing authorization with two users

This lab isolates one of the most important web-security ideas: an application must check both the actor and the object on the server.

Preparation

Build or use a local app where users can create, read, edit, and delete notes. Intentionally omit an ownership check from one action while keeping authentication correct. Give each learner two test accounts or pair learners so each controls one.

Student method

  1. Create one note as Alice and one as Bob.
  2. Capture the valid read, edit, and delete requests for each user's own note.
  3. Create a matrix of actor, object owner, action, expected result, and observed result.
  4. Repeat requests while changing only the object identifier.
  5. Confirm whether the server uses the session identity or trusts an identity field in the request.
  6. Document the exact missing check in plain language.

Expected explanation

A strong answer says more than “IDOR.” It identifies the route and action, shows that Bob's valid session can act on Alice's object, and explains that the server looked up the note by identifier without confirming ownership or permission. It also notes whether identifiers are predictable, while making clear that unpredictability alone would not fix authorization.

Defensive repair

Have learners change the server query so it selects the object by both object ID and authorized owner, or perform a centralized policy check after lookup. Add automated tests for same-owner success, different-owner denial, missing object, administrator behavior if present, and every method that touches the object.

Extensions

Replace integer IDs with UUIDs to show that the missing check remains. Move the identifier from path to JSON body. Add a bulk endpoint. Chapter 43

Guided lab: understanding injection without payload lists

The goal is to understand how data crosses into syntax. Learners should leave able to identify a source, interpreter, context, and safe boundary.

Preparation

Create a local search endpoint backed by a tiny database. Provide the vulnerable source code, a safe parameterized version, and request logging. Use only synthetic records. Keep the database and application disposable.

Read the code first

Ask learners to mark the request parameter, every transformation, the query construction, the database call, and the output rendering. They should write the final query shape with an ordinary input before trying special characters.

Build a sequence of tests

  1. Send an ordinary word that matches one record.
  2. Send a word that matches nothing.
  3. Send one quote and compare the error or behavior.
  4. Predict the complete query produced by that input.
  5. Design a harmless condition that should change the number of results if the model is correct.
  6. Confirm the server log and database behavior.

Repair and retest

Replace string concatenation with a parameterized query. Repeat every earlier test. The quote should now be treated as ordinary data. Add a regression test asserting that the query structure remains fixed and the input arrives only as a bound value.

Transfer the idea

Show short examples of shell arguments, templates, and JSON query operators. Ask learners to identify what plays the role of interpreter and syntax in each. The characters differ, but the underlying error is the same: one layer cannot distinguish intended data from executable structure.

Do not grade on memorized strings

Grade the source-to-sink explanation, predicted behavior, controlled test, and repair. A copied payload can find a bug without teaching why it exists.

Chapter 44

Guided lab: building a cryptography notebook

This lab teaches learners to write conversions and equations explicitly. The notebook becomes a record that can be checked independently.

Station 1: representation

Provide one short byte sequence as hex, Base64, decimal integers, and a Python byte literal. Ask learners to prove that all four represent the same bytes. They must print the raw length and SHA-256 digest, not merely the decoded text.

Station 2: XOR

Provide a single-byte XOR ciphertext and an expected flag prefix. Learners should try all keys, rank candidates, and verify by re-encryption. Then provide two messages encrypted with the same keystream and one likely word. Ask them to explain algebraically why the key cancels.

Station 3: modular arithmetic

Use small values so calculations can be checked by hand. Have learners compute a gcd, modular inverse, modular exponent, and CRT reconstruction. Every result should include a verification equation.

Station 4: intentionally weak RSA

Generate tiny RSA parameters for education only. Give n, e, and c. Learners factor n, calculate the totient and private exponent, decrypt the integer, convert it to bytes, and re-encrypt to verify.

Notebook standard

  • List every given value with its type and base.
  • State the unknown and the equation that connects it to known values.
  • Use exact integer operations.
  • Show byte conversions explicitly.
  • Verify each recovered value by running the forward operation.
  • End by explaining the design mistake that exposed the plaintext.

Common points of confusion

If output is unreadable, ask whether the result is definitely text. If a modular inverse fails, ask for the gcd. If RSA decryption returns leading zeros differently, discuss fixed-length blocks and integer conversion. If an answer “looks right,” ask for forward verification.

Chapter 47

Guided lab: reversing a password checker

The lab pairs static and dynamic evidence. Learners should recover the check, rewrite it in Python, and verify their model against the original program.

Program design

Create a small Linux program that reads a fixed-length input, transforms each byte using addition and XOR with an index-dependent value, and compares it with a stored byte array. Include a clear success message but no plaintext password. Compile one unstripped practice version and one stripped challenge version.

Static phase

  1. Identify format, architecture, linking, and symbols.
  2. Find the success and failure strings and their cross-references.
  3. Locate the input-length check and transformation loop.
  4. Rename variables and functions according to evidence.
  5. Write the transformation as pseudocode.

Dynamic phase

  1. Break before the final comparison.
  2. Run with a known short pattern of the correct length.
  3. Inspect input, transformed buffer, target bytes, and loop counter.
  4. Predict one output byte before executing the relevant instructions.
  5. Confirm the prediction and update the pseudocode if needed.

Model and inversion

Implement the forward transformation first. Feed the same test input and compare every transformed byte with the debugger. Only after the forward model matches should learners invert the steps to recover an accepted input. Finally, run the original program and record the success output.

Discussion

Ask which claims came from strings, which came from decompiler output, and which required runtime confirmation. Compare the stripped and unstripped versions. Discuss why patching the final branch would prove control flow but would not recover the intended input.

  • Collect only what is necessary to answer the question.

Submission

Learners provide the answer, two or more corroborating sources, exact supporting details from each, uncertainty or conflicts, and a short explanation of why less reliable results were rejected. The final section should state that no person was contacted and no private access was attempted.

Chapter 50

Helping other members learn

A club guide is only useful if members feel comfortable using it. A good explanation makes the reasoning visible and gives people room to make decisions.

Narrate the questions behind each action

When demonstrating, say what you are trying to learn before typing. “I am running file because the extension is only a claim” teaches a reusable habit. Silent speed-typing teaches students that experts know mysterious commands.

Use smaller examples

Introduce one idea with the smallest artifact that still contains it. Teach endianness with four bytes before a packet header. Teach authorization with two users and two notes before a large API. Teach a stack overwrite with a purpose-built function before a complicated network service.

Let learners predict

Pause before running a command and ask what output would support each hypothesis. Predictions turn a demonstration into an experiment. Wrong predictions are useful because they reveal the mental model that needs adjustment.

Give graduated hints

  1. Attention hint: point to the relevant artifact, request, function, or section of the prompt.
  2. Concept hint: name the idea, such as ownership checks or little-endian integers.
  3. Method hint: suggest a comparison, tool, or small experiment.
  4. Structural hint: outline the major solving steps without filling every detail.
  5. Walkthrough: teach the full solve only when the earlier levels are no longer useful.

Responding to “I have no idea”

Do not immediately give a command. Ask what the goal is, what files or endpoints exist, what one observation is certain, and what category the prompt suggests. If the learner truly lacks a prerequisite, teach that prerequisite directly and return to the challenge.

Make failure discussable

During reviews, include one approach that failed for a meaningful reason. Explain what evidence ruled it out. This helps members see that expert solving includes wrong hypotheses, careful rollback, and asking for help.

Pairing newer and experienced members

The experienced member should not take the keyboard for the entire session. Let the newer member drive. The more experienced member can ask questions, request predictions, point to documentation, and summarize progress. Switch roles briefly when demonstrating a debugging habit would help.

Keep the room safe and inclusive

State the legal boundary at the beginning of hands-on sessions. Use synthetic accounts and data. Avoid jokes about harming systems or people. Explain acronyms. Give members a way to ask privately for setup help. Credit questions and clear notes as contributions, not only flags.

End with transfer

Ask every learner to complete the sentence: “Next time I see ___, I will first check ___ because ___.” That answer reveals whether the lesson became a reusable mental model.

Part XI

Advanced topics

These chapters introduce areas that usually appear after the fundamentals. They are maps, not complete specialist manuals. Use them to recognize a challenge, identify prerequisites, and choose a safe next source.

Chapter 51

OAuth, OpenID Connect, and delegated identity

OAuth lets one application obtain limited access to another service on a user's behalf. OpenID Connect adds an identity layer. Challenges often exploit a mismatch in who issued a token, who should receive it, or where a browser is allowed to return.

Roles in an authorization flow

The resource owner is commonly the user. The client is the application requesting access. The authorization server authenticates the user and issues tokens. The resource server hosts the protected API. These roles may be run by one organization, but keeping them separate clarifies trust.

Authorization code flow

  1. The client sends the browser to the authorization endpoint with a client identifier, redirect URI, requested scope, and state.
  2. The authorization server authenticates the user and asks for consent when appropriate.
  3. The browser returns to the registered redirect URI with a short-lived authorization code.
  4. The client exchanges the code for tokens through a back-channel request.
  5. The client uses an access token at the resource server.

Important bindings

The redirect URI should be strictly validated against the client's registration. The state value binds the returning browser flow to the initiating session and helps prevent login CSRF. PKCE binds the authorization code to a secret verifier created by the client. OpenID Connect uses a nonce to bind identity tokens to a request and requires validation of issuer, audience, signature, expiration, and other claims.

CTF review questions

  • Can the redirect destination be changed through parsing tricks or an open redirect?
  • Is a code or token bound to the correct client and redirect URI?
  • Does the application validate state for the initiating session?
  • Does it confuse an access token with an identity token?
  • Are issuer, audience, signature, nonce, and expiration checked?
  • Can one account's authorization response be attached to another session?

Draw the browser redirects and server-to-server exchanges. Label where each secret or token is visible. Many confusing OAuth challenges become straightforward once every message has a sender, recipient, and intended binding.

Chapter 52

Deserialization and object reconstruction

Serialization turns structured state into bytes or text. Deserialization rebuilds objects. Some formats can invoke constructors, hooks, or general object behavior, making untrusted data dangerous.

Data formats versus object formats

JSON represents a limited collection of strings, numbers, booleans, nulls, arrays, and objects. A parser still needs schema validation, but ordinary JSON does not directly encode arbitrary executable classes. Native object serializers may preserve class names, references, types, and behavior. Examples include language-specific binary serialization, Python pickle, PHP serialization, and unsafe YAML object tags.

The core trust question

Ask who produced the serialized data and how integrity is verified. Encoding or encrypting a blob is not the same as authenticating it. A signed blob can still be dangerous if an attacker learns the signing key, the application accepts an insecure algorithm, or trusted data can be confused between purposes.

Gadget chains

A gadget is existing code that performs a useful step when an object is reconstructed, converted to a string, finalized, or otherwise used. A gadget chain links these behaviors so deserialization reaches a sensitive operation. The vulnerable application does not need an explicit function named “execute input”; available library classes may compose into the effect.

Analysis workflow

  1. Identify the format from prefixes, delimiters, source code, or errors.
  2. Decode only the transport layer and preserve the original.
  3. Determine whether the server verifies integrity before deserializing.
  4. Inventory permitted classes and lifecycle methods.
  5. Trace data from reconstructed fields into filesystem, template, network, or command operations.
  6. Use harmless effects in the lab to prove the chain.

Defensive design

Prefer simple data formats with strict schemas. Do not deserialize native objects from untrusted input. Authenticate data before parsing, separate keys and purposes, allowlist expected types, keep dependencies current, and run parsers with minimal privileges.

Do not open unknown serialized objects on your host.

Some formats execute behavior during loading. Analyze challenge samples in a disposable environment and use format-aware inspection before deserialization.

Chapter 53

Caches, reverse proxies, and request boundaries

Modern web traffic often passes through a CDN, reverse proxy, load balancer, and application server. Security problems appear when those components disagree about cache keys, paths, headers, or where one request ends.

Cache keys

A cache stores a response under a key derived from parts of the request, commonly the host and path and sometimes query parameters or headers. If an unkeyed input changes the response, one user's input may affect a response later served to others. Identify which components cache, how responses signal cache status, what is included in the key, and whether personalized content is cacheable.

Cache poisoning

A poisoning challenge usually requires three facts: an input the origin uses, the cache ignores that input when building its key, and the resulting response is cacheable. Establish normal cache behavior first. Change one header or parameter, observe the origin response, then request the baseline again without the input. Use a unique path or cache buster in a lab to avoid affecting other participants.

Cache deception

In deception, a cache is tricked into storing a personalized response under a path that appears static. Path normalization, extensions, delimiters, and routing differences can matter. Compare what the cache thinks the path represents with what the application router serves.

Request smuggling concepts

HTTP/1 requests can describe body length through Content-Length or chunked transfer encoding. If front-end and back-end components parse an ambiguous message differently, bytes considered one request by one component may become the start of another request downstream. This can disturb later traffic.

These tests are timing- and infrastructure-sensitive and can interfere with other users. Use only dedicated labs designed for the technique. Begin by identifying protocol versions, connection reuse, and parsing behavior. Never test production or shared school infrastructure.

Host and forwarding headers

Applications use host and forwarding headers to build links, select tenants, enforce allowlists, or identify the original client. A reverse proxy may overwrite, append, or trust these fields. Trace which component sets each value and never assume a client-supplied forwarding header is authoritative.

Chapter 54

Elliptic curves and digital signatures

Elliptic-curve systems use a group of points with an addition operation. Their security depends on the difficulty of recovering a scalar from a public point and on correct parameter and nonce handling.

Points and scalar multiplication

Over a finite field, an elliptic-curve equation defines a set of points plus a special identity point. Point addition combines two points. Repeatedly adding a generator point G to itself gives scalar multiplication kG. Computing kG is efficient; recovering k from G and kG is intended to be hard for suitable curves and parameters.

Public and private keys

A private key is a scalar d. The public key is the point Q = dG. Implementations must validate public points, use the correct curve and subgroup, and encode points unambiguously. Challenge bugs may involve invalid points, small subgroups, weak random keys, or custom arithmetic errors.

ECDSA nonce reuse

ECDSA creates each signature using a per-message secret nonce. Reusing the nonce for two different messages creates equations that can reveal the nonce and then the private signing key. A biased or partially leaked nonce can also be dangerous. Compare signature r values: equal r values may indicate reuse, though every parameter and hash must be handled correctly.

Signature verification

A valid signature proves that someone with the private key signed a specific message under a specific algorithm and encoding. Applications must verify the exact bytes intended, reject malformed encodings, use the correct public key, and bind context so a signature for one purpose cannot be reused for another.

CTF workflow

  1. List curve parameters, generator, order, public key, message hashes, and signatures.
  2. Check whether public points are valid and in the expected subgroup.
  3. Compare signatures for repeated components.
  4. Inspect random-number generation and nonce derivation in source.
  5. Use exact modular arithmetic and verify any recovered key by recomputing the public point or signature.
Do not implement real cryptography from scratch

Writing tiny versions is useful for learning and CTFs. Real systems should use reviewed libraries and standard protocols because validation, encoding, side channels, and error handling are easy to get wrong.

Chapter 55

Memory forensics in more depth

A memory image is a snapshot of volatile system state. Analysis begins with system context and process relationships, not a global search for passwords.

Establish image context

Record the hash and acquisition notes. Determine operating-system family, version or build, architecture, capture time, and required symbols. A plugin producing no output may mean the artifact lacks the relevant structure, the symbols are wrong, or the process existed outside the captured moment.

Process inventory and tree

List processes with identifiers, parent identifiers, creation and exit times, image paths, command lines, and session information. Compare expected parent-child relationships. An unusual name alone is weak evidence; legitimate software often has odd names, while malicious processes can copy familiar ones.

Connections and handles

Network objects can connect processes to local and remote endpoints. File and registry handles show resources a process accessed. Correlate these with command lines, loaded modules, and timestamps. One artifact should lead to another.

Injected or unusual memory

Executable private memory, mismatched permissions, suspicious thread starts, or regions not backed by ordinary modules may deserve review. These are indicators, not proof. Dump the relevant region, hash it, inspect strings and headers, and compare it with process behavior.

Credentials and sensitive data

Memory can contain secrets because applications must use them in plaintext at some point. Only search and handle the synthetic secrets required by the challenge. Do not use memory tools on real machines without authorization or expose recovered credentials in public notes.

Reporting

State the image hash, tool and symbol versions, plugin or method, process ID, virtual address where relevant, extracted artifact hash, and uncertainty. Screenshots of plugin output are supporting material; reproducible commands and interpretation are the core.

Chapter 56

Heap exploitation concepts

Heap challenges combine a program's object lifecycle with allocator behavior. Start by modeling allocations and references before studying allocator internals.

Program-level model first

Draw every menu operation. For create, edit, show, and delete, record allocation size, stored pointer, length field, index checks, and whether pointers are cleared after free. Test sequences of actions and note which state changes. Common bugs include using freed pointers, freeing twice, editing beyond an allocation, and confusing sizes or object types.

Allocator concepts

An allocator manages chunks that include user data and metadata. Freed chunks may be placed in size-based caches or bins for reuse. Exact structures and safety checks depend strongly on allocator and version. Do not copy a technique from a different libc and assume addresses or metadata rules match.

Use after free

If the program retains a pointer after freeing it, a later allocation may reuse the same memory. The stale reference can then interpret new content as the old object. A challenge may let you replace a callback, type field, or data pointer through overlapping object lifetimes.

Double free and list corruption

Freeing a chunk twice can corrupt allocator bookkeeping or make one region available through multiple paths. Modern allocators include checks and pointer protections, so the intended challenge may require a leak, intervening allocation, or different primitive.

Heap leaks

Out-of-bounds reads, stale objects, or allocator metadata may reveal heap or library addresses. Record the exact field and offset. A leak is useful only when you know what object it points into and can calculate the corresponding base.

Study workflow

  1. Identify binary, loader, and libc hashes.
  2. Reverse the menu and object structure.
  3. Create an allocation timeline for a minimal bug trigger.
  4. Observe heap state in a debugger after each operation.
  5. Name the primitive before planning a target.
  6. Make the exploit repeatable from a fresh process.

Chapter 57

Mobile application challenges

Mobile challenges usually combine an application package, platform configuration, client-side code, and network behavior. Treat the package as a structured archive before running it.

Android APK structure

An APK is a ZIP-based package containing a manifest, compiled resources, Dalvik bytecode, native libraries when present, assets, and signatures. List and hash the package, inspect the manifest, and identify architecture-specific libraries. Decompilers reconstruct Java-like code from bytecode, but names and control flow may be obfuscated.

Manifest review

Record package name, minimum and target platform versions, permissions, exported components, intent filters, deep links, backup settings, and network-security configuration. An exported activity, service, receiver, or provider may accept input from other applications. Whether that matters depends on its authorization and data handling.

Client-side secrets and checks

Search resources, assets, strings, and code for API base URLs, keys intended for public clients, hidden routes, local validation, and cryptographic parameters. A mobile app distributed to users cannot keep an embedded secret from a determined analyst. Server authorization must not depend on hiding client code.

Dynamic analysis

Use an emulator or dedicated test device, not a personal phone with important accounts. Observe logs, files, shared preferences, databases, intents, and network requests. Certificate pinning, root detection, and anti-debugging may be challenge components; understand the check before bypassing it in the lab.

Native libraries

An app may move checks into ARM or x86 native libraries. Identify exported native functions and Java Native Interface bindings, then apply ordinary static and dynamic reverse-engineering methods for that architecture.

Chapter 58

Containers, CI, and cloud-flavored challenges

Deployment files describe trust and privilege. A challenge may hide the important detail in an image layer, service account, environment variable, build job, or network boundary.

Container images

A container image consists of layers and configuration. Inspect the entrypoint, command, user, environment, working directory, exposed ports, volumes, and history. A secret copied in one build layer and deleted later can remain recoverable from the earlier layer. Multi-stage builds reduce what reaches the final image when used correctly.

Container isolation

Containers share a host kernel and are not identical to virtual machines. Capabilities, mounted sockets, host paths, device access, privileged mode, and weak runtime configuration can expand what a process can do. In a lab, inventory these boundaries rather than assuming “inside a container” means safe.

CI pipelines

Continuous-integration jobs receive source, tokens, caches, artifacts, and event data. Risks appear when untrusted pull-request content runs with secrets, shell commands interpolate unsafe values, caches cross trust boundaries, or build artifacts are substituted. Read the trigger, permissions, checkout source, environment, and secret availability in order.

Cloud identity

Cloud platforms use identities, roles, policies, tokens, and metadata services. Separate authentication from authorization. Record the principal, action, resource, and conditions for each policy. A broad wildcard, unintended role assumption, or token exposed to an untrusted workload can become the challenge path.

Orchestration manifests

Kubernetes-style manifests reveal service accounts, mounted secrets, namespaces, container privileges, volumes, probes, services, and network assumptions. A secret object is an API object, not magically encrypted merely because its values are Base64-encoded.

Use only supplied lab credentials and resources.

Cloud actions can create costs or affect shared infrastructure. Confirm the account, project, region, and scope before every command. Clean up only resources the challenge tells you to manage.

Chapter 59

Firmware and hardware challenges

Firmware is software packaged for an embedded device. Hardware challenges add physical interfaces and electrical details. Begin by identifying components and formats before connecting or writing anything.

Firmware images

Record the hash and inspect signatures, entropy, strings, and embedded filesystems. Binwalk can suggest offsets, but verify headers and extraction results. Common contents include bootloaders, kernels, compressed filesystems, configuration, certificates, web interfaces, and architecture-specific executables.

Extracted filesystem review

Search startup scripts, service configuration, web roots, update logic, hard-coded paths, users, and permissions. Symbolic links and special device files may not behave normally after extraction. Do not execute foreign-architecture programs directly on the host; use static analysis or an appropriate emulator in an isolated lab.

Serial interfaces

UART commonly uses transmit, receive, and ground lines with a configured baud rate and framing. Before connecting, identify voltage levels and pinout. Do not assume a 5-volt adapter is safe for 3.3-volt or lower logic. A logic analyzer can help infer baud and signal structure without transmitting.

SPI and I²C

SPI typically uses clock, data lines, and chip select; I²C uses clock and bidirectional data with addressed devices. Captures can be decoded when the protocol and wiring are known. Challenge clues may hide in flash transactions, display updates, or sensor traffic.

Hardware safety

Use only challenge-provided boards and documented power supplies. Confirm ground, voltage, and pin direction. Avoid writing flash until you have a verified backup. Physical mistakes can destroy equipment, unlike a script you can rerun.

Chapter 60

Signals, modulation, and radio data

Signal challenges turn changes in amplitude, frequency, phase, or timing into data. You can learn much from supplied recordings without transmitting anything.

Start with the file

Determine whether the artifact is audio, raw samples, complex I/Q data, or a tool-specific container. Record sample rate, sample format, channel count, center frequency if provided, and duration. Display a waveform, spectrum, and waterfall or spectrogram.

Time and frequency views

A waveform shows value over time and reveals pulses or symbol timing. A spectrum summarizes energy by frequency. A waterfall shows how the spectrum changes over time. Choose a window and resolution appropriate to the signal; too coarse a view can hide brief changes.

Common modulation clues

  • On-off keying: carrier energy appears and disappears.
  • Amplitude shift keying: symbols use different amplitudes.
  • Frequency shift keying: energy switches between frequencies.
  • Phase shift keying: information appears in phase changes.
  • Pulse-width or pulse-position encoding: timing or width carries symbols.

Recovering symbols

Estimate symbol duration from repeated transitions or autocorrelation. Choose thresholds, sample near symbol centers, and plot the resulting decisions. Then determine bit order, framing, preambles, checksums, and higher-level encoding. A readable ASCII fragment is evidence, but validate framing and repeated packets.

Manchester and line coding

Some encodings represent each bit by a transition, which helps clock recovery but doubles the transition rate. Identify whether high-to-low or low-to-high represents one, and confirm against a known preamble or checksum.

Legal boundary

Receiving and especially transmitting radio signals is regulated differently by location, frequency, power, and service. For club work, use organizer-provided recordings or shielded, permitted lab equipment. Do not transmit on real systems or attempt to interfere with communications.
