Learning paths

Choose projects, not a permanent identity

A path helps you decide what to do next. You do not have to specialize forever. Spend enough time in one area to build something real, then decide whether the work makes you want to continue or change direction.

A shared eight-week foundation

WeekSubjectSmall deliverable
1Files, processes, permissions, and the command lineA labeled map of a Linux process and its files
2IP, routing, DNS, TCP, and HTTPAn annotated packet capture of a web request
3Python basics and structured dataA script that parses a log and summarizes events

7Risk, privacy, ethics, and legal boundariesRules of engagement for a fictional lab

Do not wait to “finish the basics.” The foundation becomes meaningful when you reuse it in a deeper project.

Network and infrastructure security

Learn: switching, routing, subnets, DNS, DHCP, NAT, firewalls, VPNs, Linux administration, virtualization, cloud networks, identity, and logs.

Build: a small virtual network with separate user, server, and management segments. Document permitted traffic, then prove the rules with packet captures and logs.

Stretch: automate configuration checks or deploy the lab from code. The Network+ or CCNA paths can provide a syllabus.

Detection and incident response

Learn: Windows and Linux events, endpoint and network telemetry, common attack behavior, query languages, evidence handling, and incident coordination.

Build: generate safe test activity in a lab, centralize the logs, write three detections, measure false positives, and prepare a one-page triage guide for each.

Stretch: run a tabletop exercise where one member reveals evidence in stages and another keeps an incident timeline.

Secure software and application security

Learn: one web framework, HTTP, databases, sessions, access control, input handling, dependency management, testing, code review, and threat modeling.

Build: a small application with multiple roles. Write misuse cases before coding, add tests for authorization boundaries, keep secrets out of the repository, and log security-relevant actions.

Stretch: review another member’s application and submit fixes through a normal code-review process. Use the secure software guide as a checklist.

Cloud security and identity

Learn: cloud accounts and organizations, roles and policies, virtual networks, storage permissions, key management, containers, deployment pipelines, logs, and cost controls.

Build: deploy a disposable service with infrastructure as code, narrow service roles, centralized audit logs, a cost limit, and a complete teardown procedure.

Stretch: write policy checks that prevent a public storage bucket or an unrestricted administrator role.

Governance, risk, privacy, and policy

Learn: assets, threats, likelihood, impact, control design, vendor risk, privacy principles, regulation, audit evidence, and executive communication.

Build: assess a fictional student organization’s membership system. Interview a “service owner,” diagram data flow, rank risks, recommend controls, and write both a technical appendix and a one-page decision memo.

Stretch: compare two security frameworks and explain where their terminology maps, and where it does not.

CTFs, vulnerability research, and reverse engineering

Learn: assembly, debuggers, program memory, web internals, cryptographic failure modes, forensics, and responsible disclosure.

Build: complete challenges in a legal environment and write explanations centered on root cause and remediation. Then author a small challenge that teaches one idea without requiring guessing.

Stretch: reproduce a patched public vulnerability in an isolated lab and compare the vulnerable and fixed code. Start with the CTF textbook.

How to run these as a club

  1. Open with a fifteen-minute concept explanation and a clear legal scope.
  2. Spend most of the meeting building or investigating in pairs.
  3. Pause midway so groups can share observations without giving away an entire solution.
  4. End with one artifact: a diagram, commit, query, test, or short explanation.
  5. At the next meeting, revisit what failed and improve the artifact before moving on.
A useful standard for portfolio work

Another student should be able to understand the goal, recreate the setup, inspect the evidence, and see what you would improve. Clean reasoning is more valuable than a long list of tools.
