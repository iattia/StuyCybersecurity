Secure software

Security is part of engineering

A scanner at the end cannot make an application secure. Security starts with clear trust boundaries, narrow permissions, predictable failure, careful data handling, and a plan for maintenance.

Start with the system

Before looking for vulnerabilities, describe what exists. List users and services, valuable data, outside dependencies, entry points, trust boundaries, and the actions that would cause real harm.

  1. Draw the major components and data flows.
  2. Mark where data or identity crosses from one trust level to another.
  3. Write misuse cases: what might an unauthorized user, compromised account, or broken dependency try to do?
  4. Choose controls that prevent, detect, or limit each important case.
  5. Record assumptions so they can be tested when the design changes.

Authentication is not authorization

Authentication establishes who or what is making a request. Authorization decides whether that identity may perform the requested action on the requested object. Applications often authenticate correctly and still expose another user’s data because they check a role in the interface but not on the server.

  • Deny access by default and grant only what is needed.
  • Check authorization on every protected server-side action.
  • Use stable, centrally tested policy rather than scattered conditionals.
  • Test horizontal boundaries between two ordinary users as well as administrator boundaries.
  • Treat service accounts, API keys, scheduled jobs, and background workers as identities too.

Handle data according to its destination

“Sanitize the input” is too vague. Validate structure and meaning when data enters the system, then encode or parameterize it for the interpreter that will consume it.

DestinationSafer approach
SQL queryParameterized queries; do not assemble syntax from user strings.
HTML pageContext-aware output encoding and templates that escape by default.
Operating-system commandAvoid the shell; pass fixed arguments to a direct process API when necessary.
File pathResolve against an allowed directory, normalize, and enforce an explicit policy.
URL or redirectUse an allowlist of expected schemes and destinations.

Limits matter too. Set maximum request sizes, timeouts, pagination, and resource quotas so valid-looking input cannot consume unlimited work.

Protect secrets and sessions

  • Never place secrets in source code, client-side JavaScript, logs, screenshots, or example configuration.
  • Use a secret manager or protected environment appropriate to the deployment.
  • Rotate credentials after exposure and design for rotation before an emergency.
  • Hash passwords with a modern password-hashing function and per-password salts; do not encrypt them for later recovery.
  • Use secure, unpredictable session identifiers; protect cookies; expire sessions; and revoke them after important account changes.

Dependencies are part of your application

Record direct and transitive components, remove what you do not use, monitor advisories, test updates, and keep builds reproducible. A scanner can identify known issues; it cannot decide whether a package is maintained, whether its permissions are reasonable, or whether your use of it is safe.

Patch management begins before the vulnerability

If nobody knows which service owns a component, how to test it, or how to deploy an update, an urgent advisory becomes an inventory and operations crisis.

Errors, logs, and recovery

Return useful errors to users without exposing stack traces, queries, secrets, internal hosts, or object identifiers they do not need. Log enough to reconstruct important actions: authentication events, permission changes, administrative operations, data exports, and security-control failures.

Logs themselves are sensitive. Restrict access, use consistent timestamps and event fields, protect integrity, set retention, and avoid recording credentials or unnecessary personal data. Test backups by restoring them; an untested backup is only a hope.

A small project checklist

  • The repository contains setup instructions, a threat model, and no live credentials.
  • Dependencies are pinned or locked and can be updated predictably.
  • Every protected operation has a server-side authorization check.
  • Database queries are parameterized and templates escape output by default.
  • Security-relevant actions produce structured logs without sensitive values.
  • Automated tests cover normal use, denied access, malformed input, and important limits.
  • Production configuration disables debug behavior and uses secure transport.
  • There is a way to report, prioritize, fix, deploy, and learn from a vulnerability.
